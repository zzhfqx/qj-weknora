### 起容器前的依赖前提（`--no-deps` 不会帮你拉起）

侧车运行时实际依赖三件事，必须**自己保证已在跑**：

| 依赖 | 验证命令 | 没跑会怎样 |
|---|---|---|
| Redis（`redis:6379`） | `docker ps \| grep redis` | 限流失灵（代码有内存兜底，不崩） |
| PostgreSQL dev 库（`host.docker.internal:65432`） | `docker ps \| grep postgres-dev` | 鉴权直接 503（fail-closed） |
| Dev 后端（`host.docker.internal:8083`） | `curl localhost:8083/api/v1/healthz` | 所有工具调用 502 |

dev 模式下这三个都是常驻的（`make dev-fqx` 起后端，docker 里跑 postgres-dev 和 redis），所以 `--no-deps` 安全。

### 为什么共用主服务的 Redis

侧车只用 Redis 做**限流器滑动窗口**（key 前缀 `ratelimit:`），不需要持久化/ pubsub / 业务缓存。单独起一个 Redis 容器不值当。

不打架的关键是 **`REDIS_DB` 选一个不冲突的逻辑库号**（比如主服务用 db 0，侧车用 db 5）：

```bash
# .env 追加
REDIS_ADDR=redis:6379
REDIS_PASSWORD=<同主服务的 Redis 密码>
REDIS_DB=5
```

同一个 Redis 进程、不同 db 号，逻辑隔离。Redis 挂了也不致命——限流器退化为单进程内存计数。

## 已踩过的坑（2026-11-03 冒烟时实测）

### 坑 1：往 .env 追加变量撞名，意外重建了 app 容器

**现象**：跑 `up -d mcp-sidecar` 时，compose 把 WeKnora-app 也重建了（从 "Up 2 weeks" 变成 "Up 4 minutes"），且健康检查标红。

**原因**：`.env` 里原本已有 `JWT_SECRET=weknora-jwt-secret`（主服务在用），我们追加侧车配置时又写了一行 `JWT_SECRET=0025...`。docker compose 读 `.env` 时同名变量后者覆盖前者，检测到 app 的环境变量变了就触发重建。

**修法**：侧车专用密钥一律改名 `SIDECAR_JWT_SECRET`（不复用主服务的 `JWT_SECRET`）。fragment 里映射为 `- JWT_SECRET=${SIDECAR_JWT_SECRET:-}`，容器内环境变量名仍是 `JWT_SECRET`，但 `.env` 文件层面不撞名。

**教训**：往 `.env` 追加任何前，先 `grep -nE "^<变量名>" .env` 确认没有同名行。

### 坑 2：app 监听端口与 compose 健康检查/端口映射不一致

**现象**：app 进程日志打印 `Server is running at 0.0.0.0:8083`，但 compose 健康检查 curl `localhost:8080`（connection refused），端口映射 `8080:8080` 也对不上。

**原因**：`config/config.yaml` 里 `server.port` 被改成了 8083，但 docker-compose.yml 里健康检查、端口映射、以及另一个服务的 `WEKNORA_BASE_URL=http://app:8080` 全部仍写 8080。app 跑了两周没重启，旧进程一直用 8080 碰巧能过；这次意外重建后新进程读到 config.yaml 的 8083，不一致才暴露。

**修法**：统一回 8080（2026-11-03 已把 `config/config.yaml` 改回 `port: 8080`）。compose 一行没动——8080 是整个生态的标准（端口映射、健康检查、内部服务互调、dsh 包默认值全是 8080），改 config.yaml 是最小修法。

**注意**：改完 config.yaml 端口后，需要 `docker compose up -d app` 重建 app 容器才生效。前端 vite.config.ts 里的 8083 只影响本地 `npm run dev`，不影响容器部署。

### 坑 3：开发调试版有独立的 postgres 容器（WeKnora-postgres-dev）

**现象**：侧车报 `password authentication failed for user "mcp_sidecar_ro"`，但角色确实建了。

**原因**：这台机器上跑着两套独立的 PostgreSQL 容器：

- `WeKnora-postgres`（常规库，不映射宿主机端口）
- `WeKnora-postgres-dev`（开发库，宿主机映射 **65432** → 容器 5432）

开发调试版后端（`make dev-fqx`）连的是 **dev 库**。图形客户端里建角色、INSERT 端点行都在 dev 库做的，但侧车 fragment 默认连 `postgres:5432`（常规库），那里根本没有 mcp_endpoints 表。

**修法**：`SIDECAR_DB_DSN` 改成连宿主机 dev 库：

```
SIDECAR_DB_DSN=postgresql://mcp_sidecar_ro:<密码>@host.docker.internal:65432/WeKnora
```

Linux docker 默认不解析 `host.docker.internal`，fragment 里加：

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

### 坑 4：asyncpg 把 JSONB 列返回为字符串

**现象**：工具调用返回 `this tool is not enabled on this endpoint`，但端点行 tools 字段明明包含该工具。

**原因**：asyncpg 默认把 `jsonb` 列返回为 JSON 字符串（如 `"[\"a\",\"b\"]"`）而非 Python list。`_normalize_jsonb_list` 只认 list，结果 tools 和 knowledge_base_ids 都被解析为空 tuple，所有工具都被 `has_tool()` 拒绝。

**修法**：连接池创建时注册 jsonb 解码器（`endpoints.py` 的 `Database.pool()`）：

```python
async def _set_jsonb_codec(conn):
    await conn.set_type_codec("jsonb", encoder=json.dumps, decoder=json.loads,
                              schema="pg_catalog")
# create_pool(..., init=_set_jsonb_codec)
```

### 坑 5：平台 API Key 调空间接口必须带 X-Tenant-ID

**现象**：`list_knowledge_bases` 返回 `Workspace required: platform API keys must send X-Tenant-ID`。

**原因**：平台 API Key 不绑定空间，主服务 RBAC 要求每次调用显式带 `X-Tenant-ID` 头指定目标空间。侧车之前只发了 `X-API-Key`。

**修法**：`RESTClient` 每次请求从当前 Principal（contextvar）取 `endpoint.tenant_id`，自动加 `X-Tenant-ID` 头（`client.py` 的 `_tenant_headers()`）。

### 坑 6：调试版后端在宿主机跑，不在容器里

**现象**：侧车报上游连接失败，`app:8083` 主机名解析不了（`WeKnora-app` 容器已退出）。

**原因**：开发调试版后端通过 `make dev-fqx` 在**宿主机**上跑（监听 8083），不进容器。`WeKnora-app` 容器是常规部署用的，开发模式下不启动。

**修法**：fragment 里 `WEKNORA_BASE_URL` 改为 `http://host.docker.internal:8083/api/v1`（配合坑 3 的 `extra_hosts`）。

**判断方法**：`make dev-fqx-status` 显示后端 PID 在宿主机、日志路径在宿主机文件系统；`docker ps` 里 WeKnora-app 是 Exited。

### 坑 7：模型 base_url 与模型不在同一套餐（火山方舟 coding plan）

**现象**：ask 整条链路上游全 2xx（agent-chat 返回 200、SSE 也有数据），但侧车返回 "No answer could be produced"，消息表 assistant 内容空、`agent_duration_ms` 仅几百毫秒。

**原因**：智能体绑定的聊天模型 `Doubao-Seed-2.0-lite` 的 `base_url` 配成了火山方舟 **coding plan 专用端点** `https://ark.cn-beijing.volces.com/api/coding/v3`，但该模型不在 coding plan 白名单里。火山直接 404 `UnsupportedModel: The requested model does not support the coding plan feature`。智能体引擎一轮 LLM 都没跑成就挂了。

**判断方法**：grep dev 后端日志 `log.log`：

```bash
grep "LLM call failed" log.log | tail
# 看到 status 404 + UnsupportedModel + endpoint=.../api/coding/v3
```

**修法**：二选一：

1. 在网页「模型管理」把该模型的 `base_url` 改成 `https://ark.cn-beijing.volces.com/api/v3`（普通端点）；或
2. 在智能体设置里把聊天模型换成同套餐可用的模型（如 `deepseek-v4.1-flash`、`Doubao-Seed-2.1-turbo`，这两个走 coding plan 是通的）。

**注意**：这是上游模型配置问题，不是侧车问题。侧车之前把这个错误吞了（见坑 8），所以表象是 "No answer" 而不是透错。

### 坑 8：SSE 事件顺序 complete 早于 error，侧车吞了上游真实错误

**现象**：坑 7 的 404 错误在 dev 日志里明明有，但侧车 ask 返回的是兜底文案 "No answer could be produced"，没有把 `LLM call failed: ...` 透给客户端。

**原因**：agent-chat 的 SSE 事件顺序实测为 `agent_query → complete → error`。error 由 EventBus 异步派发，晚于 complete 到达。侧车 `aggregate_qa` 原来在收到 `complete` 时就 `break` 退出循环，根本看不到后面的 error 事件。

**修法**：`mcp-sidecar/app/tools/chat.py` 的 `aggregate_qa`：`complete` 只记录 `data.final_content` 做兜底，不 break；只有 `error` 事件才中断循环。这样上游真实错误会以 `failed to answer: <msg>` 形式透给客户端，不再被 "No answer" 掩盖。

**教训**：流式聚合时不要假设 complete 是最后一个事件——异步事件总线的 error 可能晚到。
