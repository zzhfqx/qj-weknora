# WeKnora v0.8.3 修改版 → v0.9.0 升级评估与建议

> **升级前版本**：WeKnora v0.8.3（修改版，分支 pg-fqx）
> **升级后版本**：WeKnora v0.9.0（官方新版，发布于 2026-10-29）
> **评估日期**：2026-11-02
> **本地源码快照**：`指南/变更文档/版本/源码/WeKnora-0.9.0/`（codeload zip，6320 文件，VERSION=0.9.0）
> **文档用途**：在**完全保证现有二开结构**的前提下，评估官方 v0.9.0 全量差异，给出选择性回填建议、迁移编号映射、风险与分阶段操作步骤。**本文档仅为建议，经审批后才执行任何变更。**

## 一、版本总览

| 维度 | v0.8.3（本地基线） | v0.9.0（官方新版） |
|------|-------------------|-------------------|

| 数据库迁移 | PG 最高官方 000123 + 自定义 093/102/103/107/120/214/215/216；SQLite 到 000016 | 官方新增 PG **000119–000134（16 个）** / SQLite **000037–000051** |

| 前端工具链 | vue3.5 / vite7 / pinia3 / TS6 | **完全一致**；npm 仅新增 jszip、@xmldom/xmldom(test) |

## 三、我们的修改在 v0.9.0 中的兼容性分析

> 方法：wiki 后端、内置 MCP、大功能依赖面、前端与杂项四个方向做了源码级 diff（本地 ↔ 快照），以下为结论。

### 3.1 Wiki 法规场景（核心二开）—— 🟡 禁止整体覆盖，仅可手工摘补丁

- `wiki_ingest.go`：本地独有 802 行 / 0.9.0 独有 494 行。本地含 13 个独有函数（4 个法规 slug 判定、callWikiLLMOnce/chatWithRetry 重试族、generatePageRelations/generateFromDocumentRelations、selectRegulationModifyPrompt）。
- `wiki_ingest_cite.go`：455 vs 34，法规 Phase1/2 整段为本地独有。
- `wiki_ingest_taxonomy.go`：217 vs 7，planRegulationSceneTaxonomy 等约 170 行纯二开。
- `prompts_wiki.go`：8 个本地独有 prompt（法规 5 个等），且共享 prompt **本地刻意译为中文，0.9.0 是英文**——英文 prompt 重写一律不跟。
- `wiki_relation_reconcile.go`：纯二开文件，上游全库无 `wiki_page_relations` 对应物，**原样保留**。
- ✅ 好消息：0.9.0 对 wiki **无架构级重构**，新增能力（扫描件 OCR、容错、占位符）多为独立纯函数，能在不碰法规分支的情况下接线。
- ⚠️ `types/wiki_page.go` 上游大量改动只是 `extensions:"x-agent"` 标签（服务内置助手 schema），不回填助手则零价值，不要制造 churn。

### 3.2 图片画廊 / smartocr（v0.8.3 已回填）—— 🟢 高度兼容

- 管线注册表、chunk_images 投影、`chunk_images_try_jsonb()`、3 个触发器、ChunkTypeImageCaption/ImageOCR 本地均已具备，0.9.0 的空图片块清理迁移（125）可直接运行。
- 0.9.0 的「OCR 预处理」属可选解析器开关；图片向量（ImageVector）仍按既有决策**不做**。

### 3.3 内置 MCP（重点二开）—— 🟢 零正面冲突

- 两侧 `internal/mcpserver/` **非测试文件同名同集（7 个）**，其中 5 个有差异，改动点均不落在二开行上。
- 二开层（mcp_user_permission 表、MCPUserIdentity 中间件、scope.go 用户交集、server.go fail-closed 与审计、mcp_user_ticket、mcp_endpoints 端点模型）在 0.9.0 中**完全无对应物，属纯叠加层**。
- 端点模型本地 types/mcp_endpoint.go 与官方 000102 设计**逐字一致**，0.9.0 端点零变化，反而降低未来合并成本。
- 凭证合一设计（入站：Bearer `mcp_xxx.JWT` + 端点 identity_mode）与 0.9.0 OAuth ClientID/Secret/assertion（**出站** MCP 客户端方向）正交，**设计落点不受影响**。

### 3.4 Agent 主链路 / 会话 —— 🔴 分歧巨大，不跟进

- session_agent_qa.go 本地 631 行 → 0.9.0 1030 行；session.go 双方 diff 约 700 行；act.go diff 216 行。
- HITL broker 1216 行、approval gate 878 行、grants/mcp_risk/ask_user/page_action 等全新包。任何跟 agent 平台化相关的改动都会牵连主链路，本期一律不动。

### 3.5 前端 —— 🟡 热点集中，wiki 主体零冲突

- **wiki/ 目录两侧文件集只差 3 个 test 和本地 2 个独有文件**，wiki 前端二开基本不受影响。
- 最大冲突热点：`KnowledgeBase.vue`（本地独有约 2042 行，法规/wiki/画廊/neo4j tab 全在此）、`KnowledgeBaseEditorModal.vue`（838 vs 988，图片管线手工合过一轮）、`chat/index.vue`（方向相反，本地独有 315 / 0.9.0 独有 1287）。
- 本地二开独有前端（Neo4jGraphViewer.vue、WikiBrowser_v1.vue、sendMsg.vue、KBIndexingStrategy.vue、TagEditDialog.vue、StorageEngineSettings.vue 等）均不与新版同名冲突。
- i18n：zh-CN 缺约 2390 行、en-US 缺约 3321 行新 key；只按所摘功能的命名空间增量补 key。

### 3.6 Neo4j 相关 —— ⚪ 全部搁置

- 独立 JSON 图谱搜索 API（#4395）：代码量小（handler 86+service 242+types 114 行），但 container.go:183 主查询绑定 `neo4jRepo.NewGraphSearchRepository`，pg 仓储仅做证据片段回查；无 Neo4j 后端则该 API 不可用。基于本地 pg `wiki_page_relations` 重写属新开发，不是移植。

## 四、关键风险点

### ⚠️ 风险 1：迁移编号冲突（已确认，沿用 +100 约定）

- 官方 `000120_tenant_assistant_config` 与本地二开 `000120_browser_authorization` **同号**。本期不导入助手迁移，本地 120 原样保留；将来任何官方 119–134 导入一律 **PG +100**（见第七节映射），SQLite 走压缩重排序（从 000017 起，**不走 +100**）。

### ⚠️ 风险 2：共享文件手工合并（不可整体覆盖）

- wiki_ingest.go / wiki_ingest_batch.go / wiki_ingest_cite.go / prompts_wiki.go、mcpserver 5 文件、KnowledgeBase.vue / KnowledgeBaseEditorModal.vue 必须 in-file 手工合并，每个接线点绕过法规/用户裁决二开分支。

### ⚠️ 风险 3：000125 数据清理不可逆性（软删，仍需备份）

- 清理走正常 chunk 软删路径并经 chunk_images 触发器同步投影。导入前备份 chunks 表；先在测试库对 ceshi2 验证命中行数与画廊表现。

### ⚠️ 风险 4：英文 prompt 漂移

- 0.9.0 多个共享 prompt 改写为英文。回填代码时**不带 prompt 文案**，保持本地中文 prompt 体系（尤其法规 5 个 prompt 与最近补齐的图片规则）。

### ⚠️ 风险 5：不要被拖入基座升级

- 工作区默认模型（134）实现时只摘 default_settings 一条线，**不要误拖 model_catalog 重构**（model_catalog.go/system_model_catalog.go 是另一条独立大线）；任何引用 sessions.kind / run_state / assistant_config / hitl 的代码都不摘。

### ✅ 风险降级因素

- Go/Node 工具链两侧完全一致；无基础设施级新依赖；无新 asynq 任务类型（Automations 用进程内 ticker，本期不涉及）；本期所有推荐项均**无强制迁移依赖**（125/134 为可选独立迁移）。

## 五、升级建议

### 📊 综合评估

**建议：继续走「选择性回填」，不做大版本整体合并。** v0.9.0 主题（agent 平台化）与本项目重心（法规 Wiki 建模 + 按用户隔离的 MCP）正交，六大件互锁且与本地 agent 主链路分叉巨大，整体跟进收益低、风险高；但版本内有一批独立、纯收益、与二开正交的小改动，值得分两批摘出。

### ⏳ 暂缓六大件的理由

内置助手 / 多智能体协作 / Automations / 审批分级 / 沙箱按用户复用 / 后台异步 shell：合计后端 1.5 万行级、前端 357 文件、container.go 装配 +551 行、迁移 119/120/121/124/126/127/128/129/130/131/132/133 共 12 个，且强耦合会话主链路。将来若明确需要其中某一件（尤其是 Automations），应单独立项，连同基座（119/120/121 + HITL + grants）整体评估，不能只摘上层。

## 九、总结

v0.9.0 是 agent 平台化大版本，其六大 headline 功能共用 HITL-审批基座、互锁成团（约 1.5 万行后端 + 357 前端文件 + 12 个迁移），与本地以法规 Wiki 和按用户隔离 MCP 为核心的二开方向正交，**整体合并无必要、风险高，建议整套暂缓**（未来若需要 Automations 等再单独立项连基座一起评估）。

与此同时，版本中有两批可安全摘取的成果：
- **Phase 1（约 1.8 人天，零迁移）**：中文单字链接修复、taxonomy 批量 embed、MCP 四注解/入参校验/metadata、HTML 抽取、RRF 面板、日志变量兼容等 9 项纯收益补丁；
- **Phase 2（约 6.5–8.5 人天，2 个独立迁移）**：**Wiki 扫描件 OCR（扫描版法规质量提升最大）**、MCP 文档级搜索、空图片块清理、工作区默认模型，以及队列释放/wkimg 容错/字节复用等 4 项稳定性增强。

全程红线：不整体覆盖任何二开文件、不碰 Neo4j、不擅改配置、PG +100/SQLite 压缩重排、英文 prompt 不跟、不升 mcp-go、git 由用户提交。**本文档为评估建议，待审批后按 Phase 分步实施。**
