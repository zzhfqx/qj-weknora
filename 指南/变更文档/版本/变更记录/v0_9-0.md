### 1.1 单汉字 Wiki 页不自动注入交叉链接

**大白话**：Wiki 会自动给正文里出现的其他页面标题加超链接。但如果知识库里有个叫「风」的单字页面，系统以前会把「风沙」「风格」「防风」这些词里的「风」字全切开、链到那个单字页，正文被切得乱七八糟。改完后：单字页面照常存在，但系统绝不再自作主张给正文里的单字加这种误链；人工或大模型明确写出的链接不受影响。

**背景**：Wiki 摄入生成页面正文后，`linkifyContent` 会扫描正文，把其中首次出现的其他 Wiki 页标题自动包成 `[[slug|标题]]` 交叉链接，让页面之间自动织成链接网。英文标题有词边界保护（`hasWordBoundary`），但**中文没有空格分词，CJK 字符一律被当作边界**——一旦知识库里存在单字标题页面（如「风」「栏」「核」），正文里的常用词就会被强行切开加链接：

- 「大漠**风**沙」→「风」被链到单字页
- 「**栏**目管理」→「栏」被链到单字页
- 「**核**心流程」→「核」被链到单字页

读者点进的往往是不相干页面，正文还被截断成链接样式。v0.9.0 官方修复了这一问题。

**核心机制**：

| 要点 | 说明 |
|------|------|
| 候选过滤 | `linkifyContent` 构建候选列表时新增 `isSingleHanRune` 判断：`matchText` 恰好为一个汉字（`utf8.DecodeRuneInString` 首 rune 字节长度等于整串长度且属于 `unicode.Han`）的 ref 直接跳过，不参与自动注入 |
| 作用边界 | 只禁止「系统自动注入」；两字及以上中文标题（如「认证」「法规」）与英文标题行为不变，长度降序优先、代码块/已有链接保护区等既有规则均不动 |
| 显式链接保留 | LLM 或人工在正文中明确写出的 `[[entity/feng\|风]]` 属于作者意图，照常渲染——这类链接在 `computeForbiddenSpans` 中本就被划为保护区域，其 slug 还会进入 `used` 集合跳过重复注入 |
| 页面保留 | 单字 Wiki 页面本身不删除、不隐藏，只是不再被自动链接，仍可通过显式链接或页面树访问 |

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `internal/application/service/wiki_linkify.go` | 修改 | 候选过滤新增单汉字跳过（+9 行，含中文注释）；新增纯函数 `isSingleHanRune`（+9 行）。`unicode`/`utf8` 导入本地原已具备，无新增 import |
| `internal/application/service/wiki_linkify_test.go` | 修改 | 补官方两个用例（断言信息汉化为中文）：①「大漠风沙」中的「风」不被自动链；②正文已有的显式 `[[entity/feng\|风]]` 原样保留且不重复注入 |

**与官方版本的差异**：

- 逻辑与官方 v0.9.0（`wiki_linkify.go` 两处补丁）完全一致；代码注释按本分支约定译为中文，官方英文注释不照搬。
- 纯函数级改动：无数据库迁移、无配置项、无前端改动；不影响法规双体系、wkimg 占位协议等任何二开逻辑。

**验证**：✅ `go build ./...` 通过；✅ `go test -run TestLinkifyContent` 全部通过（含新增 2 个用例：单字不自动链、显式单字链接保留）；✅ `gofmt` 无差异。

### 1.2 Wiki 扫描页 OCR 进入摄入

**大白话**：扫描版 PDF 就是一整页一整页的图片，里面的字是 OCR（图片识字）单独存起来的，以前生成 Wiki 时只盯着"正文文字"看，看不到这些图片页上认出的字，于是扫描版法规生成的 Wiki 页面基本是空的或靠瞎编。改完后：生成 Wiki 的三个环节（读内容、找引用、回捞证据）都会把图片页认出的文字当成正常正文一起用，扫描件也能生成有实质内容的 Wiki。

**背景**：扫描版 PDF（整页是图片、没有文字层）解析后，页面父块只有一个图片链接，可读文字全部由 VLM OCR 识别后存在**平级的 image_ocr 子块**上（`ParentChunkID` 指向图片父块；图片描述另存 image_caption 子块）。Wiki 摄入以前主要按文本父块组织内容：

- Map 阶段只取文本块，扫描页父块没有正文，`reconstructEnrichedContent` 仅在 image_info JSON 存在时内联图片信息，而 OCR 文字**未必同步进 image_info**，模型可能只看到一张图的标记，写出空壳 Wiki 或编造内容；
- 引用分类只对文本块分批，仅含图片链接的父块无法作为带正文的候选被引用；
- Reduce 阶段按 chunk ID 回捞引用证据时，同样拿不到扫描页 OCR 子块的文字。

这对扫描版法规文档影响最大。v0.9.0 官方在不改变存储结构（父块 + OCR/caption 子块不变）的前提下，从「取块、挂接」三个位置补齐。

**核心机制**（4 个纯函数 + 3 个接线点）：

| 纯函数 | 作用 |
|--------|------|
| `scannedOCRForWiki` | 从块集合中筛出「父块仅为图片链接、无正文」的启用态 image_ocr 子块；排除父块被禁用的子块；按父块 ChunkIndex、PDF 页码、子块 ChunkIndex/StartAt 稳定排序 |
| `appendScannedPageText` | 把筛出的 OCR 整页文字逐页追加到正文后；空文本、正文已包含的文本不重复追加 |
| `wikiCitationChunks` | **返回副本**：把扫描页 OCR 挂到对应图片父块的 Content 上（父块本身已有可提取正文则不动）；无父块的孤立 OCR 以文本块身份加入；库存行不变 |
| `pdfPageOf` | 从 SourceLocators 取 PDF 页码，供 OCR 子块排序 |

**三个接线点**：

| 阶段 | 文件 | 改动 |
|------|------|------|
| Map（文档→LLM 提取） | `wiki_ingest_batch.go` | 取块由全类型 `ListChunksByKnowledgeID` 改为 `ListChunksByKnowledgeIDAndTypes(Text, ImageOCR)`（caption 不进 Wiki 正文）；正文在 `reconstructEnrichedContent`（image_info 内联）之外再包一层 `appendScannedPageText`，两路互补 |
| 引用分类 | `wiki_ingest_batch.go` | `classifyChunkCitations` 入参由 `chunks` 改为 `wikiCitationChunks(chunks)`，让图片父块带 OCR 文本参与引用 |
| Reduce（引用证据回捞） | `wiki_ingest_cite.go` | 对被引且无可提取正文的父块，用 `ListChunksByParentIDs` 回捞其 image_ocr 子块，经 `scannedOCRForWiki` 校验后用 `appendScannedPageText` 拼回；同时排除 `!IsEnabled` 的证据 |

**关键边界**：
- 真实正文旁的配图 OCR（父块有正文）**不追加**——由 `chunkHasExtractableText` 判定，避免把 logo/插图 OCR 混进正文；
- image_caption 子块仍走原 image_info 内联路径（`<image>` XML），不转成正文；
- 停用的 OCR 子块或停用父块一律排除；image_info 或正文中已有的 OCR 文字不重复（恰好一次）；
- OCR 什么都没识别出来的扫描 PDF 仍由既有 `hasSufficientTextContent` 守卫拦截，拒绝让 LLM 对着图片标记编造；
- 纯内存拼装，不写库存块；无迁移、无配置、无新依赖；所依赖的两个仓储方法（`ListChunksByKnowledgeIDAndTypes`、`ListChunksByParentIDs`）本地均已存在。

### 1.3 Wiki taxonomy 目录预选改走批量 embed 池

**大白话**：Wiki 自动归类文件夹时，要先把"上百个文件夹名"和"上百个条目名"送去做向量化（变成数字好算相似度）。以前是全部塞进**一个**大请求发给模型服务，人家一次只收几条，数量一多直接拒收，归类这步就失败、退回把所有文件夹一股脑塞给大模型。改完后：自动拆成每 5 条一小车、几辆车并发跑，最后按原顺序拼好。你们法规/条款/业务对象三个固定文件夹是按命名规则直接分配的，根本不走这步，完全不受影响。

**背景**：通用 Wiki（非法规场景）以及法规场景体系B 的目录规划，需要先做一轮"目录预选"——把候选文件夹路径（如 `L1 / 深目录`）和每个条目标题+简介分别向量化，用余弦相似度筛出与本批条目最相关的文件夹，再交给 LLM 规划。旧代码对两侧文本各打**一个请求**直接调 `BatchEmbed`：知识库规模一大（文件夹上百、条目上百），单请求携带的文本条数可能超过 embedding 服务的单请求上限（通常 10～64 条，因厂商而异），整轮预选失败后只能降级"把全部目录喂给 LLM"，又可能撑爆 prompt。官方 issue #3390 即此问题。

**核心机制**：

| 要点 | 说明 |
|------|------|
| 池化向量化 | 两处直调改为经 `BatchEmbedWithPool`（本地文档切块主流程早已使用的真实池化实现，`internal/models/embedding/batch.go`）：按环境变量 `BATCH_EMBED_SIZE`（默认 5）切批，ants 协程池并发请求，结果按原顺序拼回 |
| 逐条等价 | 每批内部调的仍是同一个 `BatchEmbed`、同一个模型，因此小规模行为不变；各条向量逐条一致，相似度排序与 topK 选择结果不变——唯一差异是大规模时不再被服务端拒单 |
| 失败降级路径不变 | 向量化仍失败时依旧 Warn 后回退全量喂目录，原有兜底逻辑未动 |

**对二开法规双体系的边界（重点核实）**：

- 体系A（法规/条款/业务对象三个固定目录）是按 slug 前缀**规则式写死分配**（`planRegulationSceneTaxonomy` Step 1），不调 LLM、不调 embedding，**完全不经过本次改动的两行**；
- 只有体系B（其余通用页面）的动态目录预选经过这两个调用，且目录池事先经 `filterReservedFolders` 排除三个保留目录、LLM 结果经 `sanitizePathAgainstReserved` 二次校验，两道防线均未动；
- 无数据库迁移、无配置项、无前端改动；池化实现与 ants 池本地本来就存在，无新依赖。

| 文件 | 改动类型 | 说明 |

### 1.4 内置 MCP 只读工具补全四 annotations 注解

**大白话**：我们把搜索工具开放给千机等外部系统用时，要给每个工具贴一张"安全标签"。底层库出厂时默认把所有工具都贴成"会破坏数据、会乱连外网"，我们以前只加贴了一张"只读"，没把那两张吓人的错标签撕掉——外部系统看到的是"这工具只读但会搞破坏"，胆子小的客户端就会弹危险警告甚至不让用。改完后：8 个查询工具的四张标签一次贴齐（只读 / 不破坏 / 重复调用结果一样 / 不碰外部世界），写入类工具（提问、增删文档）保持原样。

### 1.5 MCP knowledge_base_ids 入参校验

**大白话**：外部调用搜索工具时可以传一串"只在这几个知识库里找"的名单。以前如果传的是垃圾名单（比如空字符串、混进数字），系统不报错，反而理解成"那你就是没指定"——**悄悄改成在全部知识库里搜**，范围反而放大了。改完后：只要你显式传了这个参数但格式不对，立刻报错、不启动搜索；不传才走默认范围。这道检查只管"格式对不对"，你们二开的"按用户授权取交集"在它后面，一行没动。

**背景**：search_knowledge / grep_chunks / wiki_search / ask 四个工具接受 `knowledge_base_ids` 参数让调用方收窄检索范围。旧写法用 `req.GetStringSlice(...)` 取值——该方法对类型不对的元素**静默丢弃**，且不检查空白元素。于是调用方显式传了畸形名单（如 `[" "]`、`["kb-own", 123]`、裸字符串）时，解析结果可能变成空名单，下游把空名单当作"未指定"，请求**悄悄放大成端点默认的全量范围**（fail-open）。官方 v0.9.0 在授权交集之前加了一道纯格式校验。

**核心机制**：

| 情况 | 行为 |
|------|------|
| 参数根本没传 | 返回 nil，下游走端点默认范围（含本分支"端点允许集 ∩ 用户授权集"交集） |
| 显式传了但为空白/类型不对 | 直接返回错误，工具回 `isError`，**不启动任何检索** |
| 显式传了且全合法 | 原样进入下游范围解析（id 或库名都可，规则同旧逻辑） |

校验内容：① 必须是字符串数组（`RequireStringSlice`，元素非字符串即错）；② 每个元素 TrimSpace 后非空。

**与二开的正交性（重点）**：该校验只裁参数格式，位于 `selectKnowledgeBases` / `wikiScopeFromRequest` / `resolveAskKnowledgeBases` 范围解析与用户授权交集**之前**，不读用户身份、不查 mcp_user_permission；二开的交集/fail-closed/审计链一行未动。门禁（server.go）→ 参数格式校验（本次新增）→ 端点集 ∩ 用户集（二开）→ 重授权循环，顺序清晰。

### 1.7 web_fetch 非 UTF-8 编码转码 + 抓取超时可配置

**大白话**：大模型可以替用户抓网页来读。很多中文老网站（尤其政府站）用的是 GBK 老编码，以前抓回来直接读，喂给模型的是一堆乱码；而且抓取等待时间写死 60 秒，现场想调没处调。改完后：先认出网页用的什么编码、自动转成规范的 UTF-8 再读，乱码没了；等待时间可以用环境变量 `WEKNORA_WEB_FETCH_TIMEOUT` 调（不改配置就仍是原来的 60 秒）。另外"网页太大就拒绝（正文 100KB、整包 2MB）"这条防线本地本来就有，这次核实确认，没有重复建设。

**背景**：Agent 的 `web_fetch` 工具抓取公开网页时，大量中文老站点（尤其政府/事业单位站）使用 GBK/GB2312 编码，旧逻辑不按声明编码转码，抽取出的正文是乱码，喂给模型既浪费 token 又可能被误读；同时抓取超时是写死的 60 秒常量，部署侧无法调整。

评估项原文为"非 UTF-8 声明编码转码、100KB/2MB body 上限、抓取超时"三件事，落地时核实本地代码：

| 子项 | 本地现状 | 本次处理 |
|------|---------|---------|
| body 下载上限 | **已具备**：`maxBodySize=100KB`（pipeline）、`maxAgentBodySize=2MB`（agent），超限在下载路径直接报错/截断 | 无需改动 |
| 非 UTF-8 转码 | 缺失 | **新增 `decodeHTMLBody`** |
| 抓取超时 | 写死 60s 常量 | **改为 `PageFetchTimeout()`，支持环境变量** |

**核心机制**：

1. **编码转码**：HTTP 直连读取 body 后，若 Content-Type 为 HTML，调用 `decodeHTMLBody`——已是合法 UTF-8 直接放行；否则用 `golang.org/x/net/html/charset.DetermineEncoding` 综合 BOM、HTTP 头、`<meta>` 标签判定编码并转 UTF-8；无法确定或 HTML 默认 windows-1252 但不确定时原样返回（避免把页头全 ASCII 的 UTF-8 页面转坏）。chromedp 渲染路径不经此函数（浏览器内部已处理编码）。
2. **超时可配置**：新增 `WEKNORA_WEB_FETCH_TIMEOUT`，接受 Go duration（`150s`/`3m`）或纯数字秒数（`180`，与 `WEKNORA_AGENT_LLM_TIMEOUT` 解析方式一致），未设置/非法/非正值回落默认。HTTP client、抓取 context、chromedp 三处统一使用（chromedp 截止时间是抓取 context 的子 context，预算不叠加）。

**与官方版本的差异（刻意保留）**：

- **默认超时保留本地 60s，未跟官方下调到 30s**。官方 v0.9.0 将默认从 60s 改为 30s 属于行为调优而非 bug 修复；本分支面向国内政府/法规站点，慢页面较多，60s 是既有行为，不擅自收紧；需要 30s 时部署侧设环境变量即可。已在代码注释注明该差异。
- **未摘官方同批夹带的三类改动**：① `timeoutFetchError`（浏览器渲染超时归类为可重试错误）；② SSRF 白名单 only 模式（#3378，`CheckDialWhitelistOnly`/`CheckSSRFWhitelistOnly`，还依赖 utils 新函数）；③ IPv6 不通时回退 IPv4 的多地址拨号。三者均为独立的检索/安全/网络健壮性修复，不在本项范围，保持本地现状。
- 官方超时测试位于差异巨大的 `internal/agent/tools/web_fetch_test.go`（夹带快照保存等无关重构），未整体移植。

### 1.8 Wiki 死链体检来源解析统一 + 列页 page_size 钳制

**大白话**：两个小修补打包。① Wiki 有个体检功能会查"页面引用的原始文档还在不在"，从"文档id｜标题"这种字符串里抠 id 的逻辑以前在体检代码里自己又写了一份，现在统一调用公共函数，避免两处写法以后改漏一处。② 列 Wiki 页面的接口以前不限制每页条数，有人请求"一次给我一亿页"系统就真去数据库捞一亿页（还带着正文），能把内存撑爆；现在规定一次最多 200 页、最小 1 页。你们二开的 slugs 批量预取走的是另一条独立查询，不受这个上限影响。

### 1.9 RRF 融合参数前端设置面板

**大白话**：知识库搜索其实同时用了两招——"按意思找"（向量）和"按关键词找"（关键词），两招的结果要合成一张榜单，RRF 就是合成规则。以前合成规则只能在数据库里改，管理员没有入口；现在在「检索设置」页加了三个滑块，拖一拖就能调"更看重意思"还是"更看重关键词"，存了立即生效。

**背景**：RRF（Reciprocal Rank Fusion，倒数排名融合）的三个参数——平滑常数 K、向量权重、关键词权重——后端的读写接口、配置结构、搜索融合逻辑（`retrieval_config.go` / `knowledgebase_search_fusion.go`）在之前版本已全部回填，唯一缺的是管理界面，调参必须直接改库。官方 v0.9.0 前端补了该入口。

**核心机制**：

| 控件 | 参数 | 范围/默认 | 作用 |
|------|------|-----------|------|
| 滑块 | `rrf_k` | 0～200，0 表示默认 60 | K 越大，榜首结果的优势越小，榜单越扁平 |
| 滑块 | `rrf_vector_weight` | 0～1，0 表示默认 0.7 | 向量一路在融合中的分量 |
| 滑块 | `rrf_keyword_weight` | 0～1，0 表示默认 0.3 | 关键词一路的分量；两权重之和无需等于 1 |

三个值均为可选；0/缺省时由后端 `GetEffectiveRRFK` / `GetEffectiveRRFWeights` 回落默认值。保存复用页面既有的 500ms 防抖自动保存（PUT `/tenants/kv/retrieval-config`），权限沿用仅 Admin 可编辑。

**与官方版本的差异（刻意最小化）**：

- 官方 v0.9.0 把整个 RetrievalSettings 页**重构成了 tab 布局**（basic/rrf/rerank 三页签，t-input-number 数字框 + watch 失效重建等），本地页面是旧的单页长表单。为避免把无关重构和二开面拖进来，本次**不搬 tab 重构**，只在现有单页末尾新增一个「结果融合（RRF）」分组，控件沿用本地已有的 t-slider 风格（与页面其他滑块一致）；

- 纯前端项，后端零改动、无迁移。

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `frontend/src/api/retrieval.ts` | 修改 | `RetrievalConfig` 接口加 `rrf_k?` / `rrf_vector_weight?` / `rrf_keyword_weight?` 三个可选字段 |

### 1.10 日志格式变量改名兼容（LOG_FORMAT → WEKNORA_LOG_FORMAT）

**大白话**：后端有个环境变量叫 `LOG_FORMAT`，用来规定日志每一行的排版（时间、级别、正文怎么摆），没配就用默认排版。官方觉得这名字太通用、容易跟服务器上别的软件撞名，新版改叫 `WEKNORA_LOG_FORMAT`（加自家前缀）。改完后程序**新旧两个名字都认**：先看新名字，没设再回头看旧名字。我们查过现有部署（docker-compose 透传的该值默认是空的），所以升级后行为一点不变，也不需要改任何配置；只是哪天想用自定义日志格式了，推荐写新名字。

**背景**：官方 v0.9.0 对日志类环境变量统一加 `WEKNORA_` 前缀。旧实现 `resolveLogFormatFromEnv()` 只读 `LOG_FORMAT`；官方新实现按「新变量优先、旧变量兜底」解析，并补了两道防线：模板必须含 `%msg`（否则日志正文整体丢失，属于典型配置事故）、命中旧变量时在 stderr 打一行弃用提示。

**核心机制**（[logger.go:349](../../../../internal/logger/logger.go) `resolveLogFormatFromEnv`）：

1. `os.LookupEnv("WEKNORA_LOG_FORMAT")`——注意用的是 LookupEnv 而非 Getenv：**新变量显式设为空串也算"已设置"**，此时不回落旧变量（与官方语义一致，允许用空值显式关闭自定义模板）；
2. 新变量完全未设置时，回落读 `LOG_FORMAT`；
3. 两者 trim 后皆空 → 返回空串，由内置默认格式兜底；
4. 非空模板若不含 `%msg` → stderr 报错（指明是哪个变量）并返回空串回退默认，**不让错误模板把日志正文吞掉**；
5. 命中的是旧变量且模板合法 → 生效，同时 stderr 打一行中文弃用提示（仅提示，不阻断）。

调用点（[logger.go:272](../../../../internal/logger/logger.go)）与 `threadNeeded: strings.Contains(tmpl, "%thread")` 逻辑均不变。

**与官方版本的差异**：

- 逻辑与官方逐行等价；唯一差异是 stderr 两行提示文案**汉化为中文**（本地代码注释与面向运维的输出统一中文体系），测试断言同步按中文文案编写；
- **未修改任何现有配置文件**：`.env.example`（`# LOG_FORMAT=` 注释态）、`docker-compose.yml`（`LOG_FORMAT=${LOG_FORMAT:-}` 透传）、CI workflow 全部原样保留——默认空值下既不会触发弃用提示，也不会触发 `%msg` 报错，升级零噪音；
- 无迁移、无前端改动。

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `internal/logger/logger.go` | 修改 | `resolveLogFormatFromEnv` 改为新名优先+旧名回落，补 `%msg` 守卫与弃用提示，注释汉化 |
| `internal/logger/logger_test.go` | 修改 | 移植官方 `TestResolveLogFormatFromEnv`（11 个子用例），警告断言改中文；新增 `io`/`os` import |

**验证**：✅ `go test -vet=off -count=1 ./internal/logger/` 全部通过（含 11 个新子用例：两者皆空/新变量生效/新名覆盖旧名/显式空串不回落/纯空白不回落/trim/旧名回落+弃用提示/新旧变量缺 `%msg` 各被拒）；✅ 反向验证：临时关掉 `%msg` 守卫，3 个守卫类子用例如约 FAIL，还原后转绿；✅ `go build ./...` 全量通过。

### 1.11 MCP search_knowledge 支持文档级范围 knowledge_ids（Phase 2 首发）

**大白话**：外部系统（千机等）调我们的 `search_knowledge` 搜索工具时，以前只能说"在这几个**知识库**里找"；现在可以多传一个 `knowledge_ids` 参数，直接说"只在这 1～100 份**文档**里找"——名单来自 `list_documents` 或上次搜索结果。范围在开搜之前就圈死，每一份文档都要验明正身：存在、在这个调用方被授权的知识库里、文档属主租户对得上，任何一个不满足立刻报错，绝不偷偷扩大范围。二开的"按用户授权取交集"在校验之前执行，一行没动。顺带修了一个"说明书与实物不符"：`read_document` 的 query 参数对外描述一直写"按整句短语匹配"，但底层实际早就改成了"拆成词、每个词都出现即可、顺序不限"，这次只把描述文字改成与实际行为一致，**匹配行为零变化**。

**背景**：官方 v0.9.0（#4463）为内置 MCP 服务端的 `search_knowledge` 增加文档级精确限定。本地的运行时底座（`types.SearchTarget.KnowledgeIDs`、`SearchParams.KnowledgeIDs` → `HybridSearch` 仓储过滤、`DisableRecallThresholds`）在之前版本已全部回填，只差 MCP 层的入参、校验与聚合逻辑。

**核心机制**：

1. **工具 schema**（[tools_retrieve.go:57](../../../../internal/mcpserver/tools_retrieve.go)）：`knowledge_ids` 声明为可选字符串数组，`minItems=1, maxItems=100, items.minLength=1`；省略=整库搜索（与旧行为完全一致）。
2. **处理器分支**（`handleSearchKnowledge`）：先照旧走 endpoint 授权 → 二开用户交集 → `knowledge_base_ids` 选择 → 可检索库过滤；**仅当显式传入 knowledge_ids 时**，用 `RequireStringSlice` 取名单（类型畸形直接报错，与 1.5 同一 fail-closed 纪律），再交 `documentSearchTargets` 收窄。
3. **文档级目标聚合**（[scope.go](../../../../internal/mcpserver/scope.go) `documentSearchTargets`）：
   - 空名单 / 超 100 个：**在任何文档 I/O 之前**拒绝（有测试计数保证）；
   - 逐个 trim、去空白、去重；每个 id 经新抽出的 `knowledgeInKnowledgeBases` 校验：文档存在 + 属于已授权且已选中的知识库 + 文档租户 == 知识库租户（共享库存放在属主租户下，最后一条防伪造属主越权）；
   - 同一知识库的多份文档合并为一个 `Type=knowledge` 的 target，带 `DisableRecallThresholds=true`——范围已被显式圈死，放宽向量/关键词阈值，避免"指定了文档却因阈值差一点一篇都召不回"；
   - `knowledgeInScope`（read_document 用）改为复用 `knowledgeInKnowledgeBases`，两处授权判断从此只有一份实现。
4. **执行函数收窄**：`runSearchKnowledgeWithFilter` 签名从收 `kbs` 改为直接收 `types.SearchTargets`，底层工具透传链路 `SearchTarget.KnowledgeIDs → SearchParams.KnowledgeIDs → HybridSearch` 早已就绪（[search_knowledge.go:720](../../../../internal/agent/tools/search_knowledge.go#L720)）。
5. **read_document 描述对齐**：query/offset/limit 三处描述更新为官方 v0.9.0 文案（拆词匹配、offset 0-based、query 模式下 limit 不生效等），纯英文 schema 描述，面向外部调用方。

**与官方版本的差异**：

- 生产代码逻辑与官方**逐行等价**（含 100 上限、空白拒绝、trim 去重、租户校验、阈值放宽）；错误文案保留英文，与 1.5 一致（回给外部 MCP 调用方）；
- **未移植官方 RPC 级测试夹具**（`stubKBService`/`stubKnowledgeService`/`mcpCallContext`/`rpc` 等本地不存在，整套夹具迁入代价大且会碰到二开的用户授权链），按 1.5 既定策略改写为**纯函数级测试**直接驱动 `documentSearchTargets`，覆盖官方测试的全部判定分支（含官方"越权/伪造属主/100 边界/先于 I/O 拒绝"四类断言）；
