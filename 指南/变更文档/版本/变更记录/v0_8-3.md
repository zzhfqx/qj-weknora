## 一、版本升级（官方 v0.8.3 移植）

### 1.1 Wiki 写保护（表行丢失拒绝）

**背景**：Wiki 摄入过程中，LLM 对页面进行整页重写时，可能会意外丢失表格行。v0.8.3 官方新增写保护机制：新写入内容缺少已存储页面的表格行实体时，拒绝写入并保留原页面。

**核心机制**：
- **Agent 整页写入（严格）**：丢失任何表格行都拒绝（零容忍）
- **Wiki 摄入 Pipeline（宽容）**：允许最多 20% 的行丢失（去重是合法操作），超过才拒绝
- 行标识取表格第一列的实体名称，忽略强调标记（`**bold**`、`*italic*` 等）

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `internal/application/service/wiki_write_row_guard.go` | **新增** | 表行保护核心逻辑（187 行） |
| `internal/application/service/wiki_page.go` | 修改 | `UpdatePage` 统一入口接入写保护 |

**关键常量**：
- `wikiWriteIngestRowIdentityLossLimit = 0.20` — 摄入阶段容忍 20% 行丢失
- `wikiWriteGuardLogLimit = 5` — 拒绝日志最多列出 5 个丢失的行标识

**与官方版本的差异**：
- 省略了 `types.WikiShrinkAllowedFromContext`（v0.8.0 无此机制）
- 省略了 `common.PipelineWarn`（仅日志告警，非核心功能）

**验证**：✅ 全量编译通过

### 1.4 检索质量优化

包含三项改进：RRF 融合排序修正、MMR 去重性能优化、跳过摘要意图检索。

**1. RRF 排序优化**

- **问题**：混合检索时 RRF 分数（~0.016 量级）远小于单检索器分数（0-1 或 >10），导致混合结果总是输给纯向量/纯关键词结果，rerank 的 base 项和 MMR 的 relevance 项也近乎失效
- **修复**：
  - 多列表最佳排名：每个 chunk 在向量/关键词的多个 store group 中取最佳排名，而不是扁平拼接后排
  - RRF 分数归一化到 [0, 1]：除以理论最大值 `(vectorWeight+keywordWeight)/(k+1)`
  - BM25 分数缩放：关键词-only 路径将无界 BM25 分数除以列表最高分，归一化到 [0, 1]

**2. MMR 去重优化**

- **问题**：原实现每选一个结果就要遍历所有剩余候选做 Jaccard 计算，O(k*n) 复杂度
- **修复**：
  - 基于倒排索引（postings list）的稀疏更新：只对共享 token 的候选计算交集，不相交的文档完全跳过
  - k=1 快速路径：直接选最高分，跳过段落 token 化和 postings 构建
  - 外部签名完全兼容（`SelectMMR(ctx, results, k, lambda)` 不变）

**3. 跳过摘要意图**

- **行为变化**：`summarize` 意图不再触发知识库检索，直接使用已有上下文做纯 LLM 摘要
- **配套增强**：新增 `NormalizeQueryIntent` 规范化函数，处理大小写、连字符/空格差异，未知意图归为空（安全默认）
- 非检索意图自动应用专属 system prompt（已有机制，无需改动）

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `internal/reranking/mmr.go` | 修改 | postings 倒排索引实现 + k=1 快路径 |
| `internal/application/service/knowledgebase_search_fusion.go` | 修改 | classify 返回二维切片、RRF 归一化、BM25 缩放、bestRanks |
| `internal/application/service/knowledgebase_search.go` | 修改 | 调用方适配二维切片 |

### 1.6 Wiki follow-up 并发健壮性增强

针对 Wiki 摄入动态扇出机制的健壮性加固，确保并发控制在失败、panic、写保护拒绝等异常场景下行为正确。

**修复内容**：

| 修复项 | 说明 |
|--------|------|
| 失败不释放预留 | `ProcessWikiIngest` 改用命名返回值 `retErr`，defer 中只有 `retErr == nil` 才释放 follow-up 预留。失败时 asynq 会重试，预留保留给重试继续使用，避免重试时槽位已被其他批次占满 |
| Panic 保留预留 | defer recover 捕获 panic 后重新抛出，不释放预留。asynq 重试机制接管，预留随重试自然续期 |
| 写保护延期更新（updateDeferred） | 表行写保护拒绝写入时（`ErrWikiWriteDroppedTableRows`），不算错误也不算成功，该 slug 的所有贡献文档标记为 unapplied，保留到下一批次处理，避免 trim 阶段误删导致更新永久丢失 |
| classifyWikiPageWrite | 统一封装写保护错误分类逻辑，将写入结果转为 `(deferred, err)` 对 |

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `internal/application/service/wiki_ingest_batch.go` | 修改 | `ProcessWikiIngest` 命名返回 + defer 释放；`reduceSlugUpdates` 增加 `updateDeferred` 返回值；新增 `classifyWikiPageWrite`；reduce 循环增加 updateDeferred 分支 |

**关键设计**：
- **成功才释放**：预留槽位在失败/重试时不释放，保证重试任务能立即获得槽位
- **写保护非失败**：表行丢失拒绝是质量保护机制，不是错误，走延期而非重试预算
- **defer 顺序**：两个 defer — 外层统计日志先注册（后执行），内层释放逻辑后注册（先执行），确保释放时 retErr 已确定

**与官方版本的差异**：
- 未实现租户删除防护（`tenantIsDeleted`）：需新增 `TaskPendingOpsTenantLiveness` 接口及 repo 实现，改动较大，暂缓
- 未实现不可用 Wiki 队列排空（`releaseIngestForUnavailableWiki`）：需新增 `TaskPendingOpsDrainer` 接口，暂缓
- 未改动 `finalizeWikiSubtask` 的 attempt 参数：当前版本 subtask 释放逻辑不依赖 attempt

**验证**：✅ 全量编译通过

### 1.7 Wiki 反链标题解析

**背景**：之前 Wiki 页面的反链列表（"被引用"区）显示的是反链 slug，如果反链页面不在当前侧边栏已加载范围内，就只能显示 slug（如 `concept/gong-si-zi-ben-zhi-du`），用户体验差。v0.8.3 官方在页面详情接口中增加 `in_link_titles` 字段，一次返回所有反链的标题。

**核心机制**：

| 层级 | 说明 |
|------|------|
| 后端 types | 新增 `WikiPageDetail` 类型，内嵌 `WikiPage` + `InLinkTitles map[string]string` |
| 后端 handler | `GetPage` 查询页面后，分批查询所有反链 slug 对应的标题（每批 1000 个），与页面数据一起返回 |
| 前端工具 | `wikiBacklinkTitles.ts`：`resolveWikiBacklinkTitle(slug, titles, pages)` 三级解析（接口 titles → 已加载 pages → slug 兜底） |
| 前端展示 | 反链列表使用 `resolveWikiBacklinkTitle` 替代 `slugDisplayName`，未加载页面也能显示中文标题 |

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `internal/types/wiki_page.go` | 修改 | 新增 `WikiPageDetail` 类型 |
| `internal/handler/wiki_page.go` | 修改 | `GetPage` 返回 `WikiPageDetail`，批量查询反链标题 |
| `frontend/src/views/knowledge/wiki/wikiBacklinkTitles.ts` | **新增** | 反链标题解析工具函数 |
| `frontend/src/views/knowledge/wiki/WikiBrowser.vue` | 修改 | 新增 `inLinkTitles` 响应式变量；反链显示使用新解析函数 |

**性能考量**：
- 后端批量查询（`ListBySlugs`）代替逐个 `GetPageBySlug`，1 次查询 vs N 次查询
- 前端不再需要为反链做 `preloadLinkedPageTitles` 的 in_links 预加载（out_links 和关系仍保留预加载）
- 分批大小 1000，防止 SQL 参数数量爆炸

**向后兼容**：
- 接口是增量字段（`in_link_titles`），老客户端忽略该字段不影响使用
- 前端兜底：如果接口没返回 `in_link_titles`，回退到已加载页面 + slug 兜底

**与官方版本的差异**：
- 保留了 `preloadLinkedPageTitles` 用于 out_links 和关系页面（官方可能也保留了，本改动不涉及 out_links 优化）
- 未对 out_links 做同样优化，因为 out_links 页面可以在正文渲染时点击后再加载，优先级较低

**验证**：✅ 后端全量编译通过；✅ 前端 TS 类型检查通过

### 1.8 原文引用导航（引用回指原文件并定位高亮）

**背景**：此前聊天回答中的引用只能打开引用列表查看片段文本，无法回到原始文件的实际位置。法规场景下，用户需要核对条款原文，引用必须能直接跳转到 PDF 页码/区域、Word 段落、Markdown 段落、Excel 行、PPTX 幻灯片、图片区域或音频时间点。v0.8.3 官方新增 `SourceLocator` 机制，本次完整移植该链路。

**核心机制**：

| 层级 | 说明 |
|------|------|
| 解析层（docreader） | 解析结果新增 `source_blocks`：Markdown 字符区间 + `locator_json`；PDF 输出页码与页面比例 bbox（左上原点、1 基序号），Excel 输出工作表名与行范围 |
| 传输层（Go） | gRPC / HTTP 解析器透传 `SourceBlock`；`ReadResult`、`ParsedChunk`、`ParsedParentChunk` 携带定位器 |
| 存储与检索 | `Chunk.SourceLocators` 以 JSON 字段落库；切片、图片多模态、知识库检索结果、会话引用等链路均透传定位器与来源 chunk ID |
| 前端定位 | 结构化定位器优先（页码/bbox、docx block、slide、sheet 行、text 偏移、time、section），再在区域内做引文细化，最后全文唯一匹配与表格/片段兜底；匹配前做 NFKC + 小写 + 符号归一化，拒绝数字子串误配 |
| 前端展示 | 引用点击直接进入抽屉「原文」模式；PDF 使用 pdf.js 渲染文本层并高亮 bbox/文本，Word 按块与内嵌图片摘要定位，Markdown 建立完整原文区域后逐句缩小，Excel 按行、PPTX 按幻灯片、图片按 bbox、音频按时间点定位；定位失败或原文已变更时给出明确状态提示 |

### 1.10 图片画廊 + 图片属性观察管线（chunk_images / smartocr）

**背景**：本地此前只有"文档正文里嵌图"的渲染，没有统一的图片浏览入口，也不会对抽取出来的图片做 caption/OCR 之外的属性归纳。v0.8.3 官方把图片画廊从无到有补齐：以数据库投影表 `chunk_images` 把 `chunks.image_info` 里的图片摊平成可分页、可搜索、可筛选的列表，并配套一条"图片属性观察"管线（smartocr），让模型在出 caption/OCR 的同时归纳图片属性。本次按阶段移植：先上画廊读侧，再上属性观察管线。

**核心机制**：

1. **chunk_images 投影表（画廊读侧）**
   - 不引入独立 ORM 模型：`chunk_images` 由数据库触发器（insert/update/delete 三个）随 `chunks.image_info` 自动维护，每个 image_info 元素一行，caption、ocr_text、观察到的 attrs 各占一列，画廊不必每次请求都解析每个图片 chunk 的 JSON。
   - 同一张图被多个 chunk 复制时只列一次：查询用带索引的反连接（winnerClause）取"最近更新 chunk 上的那个副本"；按来源文档筛选时用 scopedWinnerClause 把副本范围限定在所列文档内，范围外的副本不得遮蔽同图。
   - 迁移自带存量回填：把所有未删除图片 chunk 的 image_info 一次性投影进表，画廊上线即有图。
   - **迁移编号**：本地先定为 `000213`，但存量库 schema_migrations 已推进到 214，而 golang-migrate 只向前跑、永远不补跑低于当前版本的迁移，因此重排为 **`000215_chunk_images`**（SQLite 压缩序列对应 `000015`，不走 +100）。

2. **画廊读接口与前端**
   - 后端：`ListImageAssets`（仓储）+ `ListImagesByKnowledgeBaseID`（服务）+ handler 的 `ListImages`/`ListImagesPost`/`GetGalleryConfig`；路由 `GET/POST /knowledge-bases/:id/images`、`GET /knowledge-bases/:id/gallery-config`，沿用本地 Viewer + KBAccessRead 鉴权。
   - 前端：知识库 tab 新增「画廊」，`ImageGallery.vue`（瀑布流分页、关键字搜索、按来源文档筛选、启停/排序）、`GalleryViewer.vue`（大图查看器，右侧显示图片描述/图中文字/基本信息）、`GallerySourcePicker.vue`（按文档筛选）、`galleryImageSrc.ts`（图片经 KB 文件代理加载）。

3. **图片属性观察 + smartocr 管线**
   - `image_info` JSON 增量带 `attrs`（观察到的属性）与 `sha256`（原图摘要），寄生在现有 `image:multimodal` asynq 任务上，**不新增任务类型、不新增 DI**；管线靠 Go `init()` 包级注册。
   - 内置两条管线：`default`（caption+OCR，行为同升级前）与 `smartocr`（一次 VLM 请求同时观察属性 + caption，再用纯函数 `DecideOCR` 决定是否真的跑 OCR——观察到 `contain.text=block` 或 `data_visual=true` 才跑，观察失败按保守兜底跑 OCR，可省 OCR 调用）。
   - KB「多模态」区新增 `ImagePipelineSettings.vue`：选管线、看属性 schema；`ImageAttrsEnabled`/`ImagePipelineID`/`ImagePipelineParams` 随 KB 配置落库，加工时快照进任务载荷；在途旧任务解包无新字段时回退 default，滚动升级安全。

4. **抽取图片资源授权绑定（bindStoredImages）**
   - **现象**：画廊图片能列出、却加载失败（broken）。根因不是图片没存（resources 表有记录、磁盘文件在），而是**没授权**：KB 作用域的文件代理只服务在 `resource_bindings` 表里有显式绑定（owner_type=knowledge、relation=extracted_image）的资源；本地此前完全缺失官方的 `bindStoredImages`，image 资源 0 个绑定，跨工作区查看一律 403。
   - **修复**：移植 `bindStoredImages`，在 docreader 解析路径（解析完即绑）与手动录入路径两个调用点，把本次抽取落盘的图片资源尽力绑定到所属知识；绑定失败只告警、不让解析失败（一次解析代价高昂，漏掉一次认领退化为同工作区渲染，而非让文档解析失败）。
   - **存量数据**：对已落库但未绑定的图片跑了一次幂等回填（按 chunks.image_info 里的 `resource://` handle 反查 resources 再补绑），唯一索引 `(resource_id, owner_type, owner_id, relation)` 保证不重复。

### 2.1 Wiki 关系页面标题解析与关系对账

**背景**：Wiki 页面详情的"本体关系"区中，对端页面（正向关系的目标、反向关系的源）之前只显示 slug（如 `clause-gy-sy-hlwx-bx-c-3`），用户体验差。v0.8.3 官方只做了 in_links 反链标题解析，关系页面标题是我们在法规场景下的延伸优化。

随后发现：页面在重新解析、去重合并、条款质检时会被软删除，新页面常以新 slug 生成，而关系表只增不删，导致大量关系指向已删除页面——标题解析命中失败后退化为英文 slug（去掉 `entity/` 前缀），点击跳转也返回 404。为此新增实体关系对账机制。

**核心机制**：

| 层级 | 说明 |
|------|------|
| 后端 handler | `GetPageRelations` 查询关系后，收集所有对端 slug，批量调用 `ListBySlugs` 查询标题，组装为 `titles: { slug: title }` map 与关系数据一起返回 |
| 关系对账 | finalize 末尾（以及删除页面后）对整个知识库的关系做对账：端点存活则不变；端点已删除但存在同「页面类型 + 标题」的**唯一**存活页面时改写到新 slug；找不到等价页面则删除该关系；改写后重复的关系只保留一条（优先保留原本就是该对端点的行） |

### 2.2 链接标题预取批量查询（消除死链 404）

**背景**：切换 Wiki 页面时，前端会预取当前页 `in_links/out_links` 中、左侧页面树尚未加载的 slug 对应页面，以显示中文标题。早期实现对每个 slug 逐个请求页面详情；而这些 slug 中既有未加载的真实页面，也有 LLM 写出的幻觉死链（引用的页面从未被创建），每个死链产生一条 404，日志中出现成片 `Wiki page not found`。

**核心机制**：

| 层级 | 说明 |
|------|------|
| 前端 API | `listWikiPages` 新增 `slugs` 批量参数（逗号拼接） |
| 前端预取 | `preloadLinkedPageTitles` 由 N 个单页请求改为 **1 次批量请求**，返回结果按 slug 去重后追加 |
| 后端 handler | `ListPages` 解析 `slugs` 参数（逗号分隔、逐项去空白） |
| 后端 service | 携带 Slugs 时走 `ListBySlugs` 做一条 IN 查询，只返回真实存在的存活页面轻量投影，不存在的 slug 静默缺失（HTTP 200，不产生 404） |

**涉及文件**：

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `frontend/src/api/wiki/index.ts` | 修改 | `listWikiPages` 支持 `slugs` 数组参数 |

| `internal/application/service/wiki_page.go` | 修改 | `ListPages` 新增 Slugs 批量分支 |
| `internal/types/wiki_page.go` | 修改 | `WikiPageListRequest` 新增 Slugs 字段 |

**验证**：✅ `go build ./...` 通过；✅ 前端 TS 类型检查通过；✅ SQL 实测真实/幻觉 slug 混传时只返回真实存活页面

### 2.3 内置 MCP 按用户身份裁决（多租户隔离）

**背景**：千机智能体问答链路为「千机用户 → 智能体网关 → 单 `opencode serve` 多用户目录 → weknora 内置 MCP（12 工具）」。官方内置 MCP 的 `/mcp/:endpoint_id` 只做端点 Bearer 鉴权，通过后所有调用统一成为机器用户 `mcp-<endpointID>`，scope 仅由端点的工具白名单 + 知识库列表推导——**同一端点背后的所有千机用户权限等价**，无法满足"壳内用户想干嘛就干嘛，只要无法获取其它壳内子进程的信息"的隔离要求。二开在不改动官方鉴权逻辑的前提下，于其后增加一层"用户身份裁决"。

**总体链路**：网关在验千机登录态得到 user_id 后，转发每个 MCP 请求时注入两头——`Authorization: Bearer mcp_...`（固定端点令牌，原有鉴权，证明"是我方 OpenCode 集群"）+ `X-User-Credential: <mcp_user_identity JWT>`（新增，证明"背后是哪个千机用户"）。weknora 侧原有 `MCPEndpointAuth` 不动，其后挂新中间件做验签与交叉校验，再在官方既有的两道裁决关卡（`filterTools` / `guardTool`）和知识库范围函数（`allowedKnowledgeBases`）内做按人交集。

**核心机制**：

| 层级 | 说明 |
|------|------|
| 身份票据 | HS256 短期 JWT（复用 `JWT_SECRET`，与登录 token 同一密钥体系），claims 为 `{type:"mcp_user_identity", sub:千机user_id, tid:工作空间id, aud:endpoint_id, iat, exp, jti}`；默认 TTL 5 分钟，网关按请求即时签发，短 TTL 不影响 SSE 长连（鉴权发生在 HTTP 请求建立时）。独立 `type` 值防止与登录 access token / sandbox 票据混用 |
| 身份中间件 | 读 `X-User-Credential` 头：无头、验签失败、过期、`tid≠端点工作空间`、`aud≠端点id` 一律 **401 fail-closed**，绝不退化为机器用户全开；通过后 user_id 同时写入 gin keys 与 request context（纪律同 `applyAuthSession`）。提供灰度开关 `MCP_REQUIRE_USER_IDENTITY`（默认 true；false 时仅对无头调用告警放行，供过渡期排障） |
| 工具裁决（二元） | 本期端点只开 9 个只读工具（3 个 ingest 写工具不在端点白名单），故可用性是二元的：用户授权知识库列表**非空** → 端点白名单内工具可见/可调；**无行或空列表** → tools/list 返回空、按名直调返回 `tool not permitted for this user`（不泄露授权明细）。tools/list 与 tools/call 两侧同等校验 |
| 知识库交集 | `allowedKnowledgeBases` 产出端点允许集后，再与该用户在 `mcp_user_permission` 行内的 kb_id 列表取交集；端点未限定库（全集）时同样交集。列表中已删除/跨工作空间的失效 id 由官方既有的逐个重授权循环 warn-and-continue 静默丢弃；`knowledgeInScope` 复核单文档自动继承按人收窄，无需改任何工具 handler |
| 授权表 | 新增**一张**二开表 `mcp_user_permission`，**一个用户只有一行**：`(tenant_id, user_id, knowledge_base_ids JSON 数组)`，UNIQUE(tenant_id,user_id)。建库=upsert 追加、共享=append 去重、收回=移除。该表由千机建库/共享业务流程写入，weknora MCP 层只读，不建 weknora 影子用户 |
| 缓存 | 进程内 45s TTL（建议区间 30–60s），权限变更最迟 45s 生效；**空结果不做负缓存**（"刚建库立刻首次提问"是正常路径），且撤销/删行后的本次读取立即清除旧快照；定时 sweep 防 map 无限增长 |
| 审计 | 每次 tools/call 输出结构化日志（`logger.Fields`）：user_id、endpoint_id、tool、参数中的 knowledge_base_id/knowledge_id、verdict=allow/deny、deny_reason、request_id，可按千机 user_id 追溯 |
| 并发纪律 | user_id 只从验签后的 request context 取并随 ctx 下传；无任何包级变量/struct 字段缓存"当前用户"（MCP transport 为 stateless，全局变量必串用户） |

**安全要点**：MCP 请求中的 kb_id/knowledge_id 是模型生成的工具参数，可能被工具返回内容中的 prompt 注入篡改为他人 ID；裁决用 user_id 只采信服务端验签票据，工具参数/URL/请求体中的明文字段一律不采信。持 A 用户合法签名构造 B 的 kb_id 调用会被交集拒绝（红队必测项）。
