## 一、大文件上传修复（已完成升级 ✅）

### 背景

v0.8.0 修改版中，我们通过在 `uploadKnowledgeFile` 中硬编码 `{ timeout: 300000 }` 解决了大文件上传超时问题。

v0.8.2 官方实现了更优雅的**动态超时方案**：根据 FormData 中文件大小自动计算超时，小文件用下限（5 分钟），大文件按 10MB/min 线性增长。

### 调整内容

#### 1.1 新增动态超时工具模块

**文件**：`frontend/src/utils/requestTimeouts.ts`（**新增**，从 v0.8.2 官方移植）

**核心 API**：

| 函数/常量 | 说明 |
|----------|------|
| `UPLOAD_TIMEOUT_FLOOR_MS` | 上传超时下限：5 分钟 |
| `uploadPayloadBytes(data)` | 计算 FormData 中所有 Blob/File 的总字节数 |
| `uploadTimeoutMs(data)` | 动态计算超时：`max(5min, 文件大小 / 10MB * 60s)` |
| `isTimeoutError(error)` | 判断请求失败是否为超时（覆盖 ECONNABORTED / ETIMEDOUT / message 含 timeout） |

#### 1.2 `postUpload` 统一应用动态超时

**文件**：`frontend/src/utils/request.ts`（修改）

在 `postUpload` 函数中新增动态超时：
```typescript
return instance.post(url, data, {
  timeout: uploadTimeoutMs(data),  // 新增
  ...config,                         // 显式 config.timeout 仍可覆盖
  // ...
})
```

**优势**：所有调用 `postUpload` 的上传接口（知识文件上传、技能包上传、模型上传等）自动获得动态超时，无需每个接口单独配置。

#### 1.3 移除 `uploadKnowledgeFile` 中的硬编码超时

**文件**：`frontend/src/api/knowledge-base/index.ts`（修改）

```diff
- return postUpload(url, formData, onProgress, { timeout: 300000 });
+ return postUpload(url, formData, onProgress);
```

改为依赖 `postUpload` 的统一动态超时。

#### 1.4 保留：上传失败原因提示增强

**文件**：`frontend/src/views/knowledge/KnowledgeBase.vue`（保留并优化）

- `getUploadFailureReason`：详细的失败原因分类（重复文件、超时、网络错误、后端 message）**全部保留**
- **优化**：超时判断从内联检查改为复用 `isTimeoutError` 工具函数（覆盖更多超时场景，如 `ETIMEDOUT`）
- `showUploadResultMessages`：批量上传失败时显示失败文件详情列表 **全部保留**

#### 1.5 保留：后端上传耗时日志

**文件**：`internal/application/service/knowledge_create.go`（保留）

- 开始时记录文件名 + 大小
- 重复文件跳过时记录耗时
- 完成时记录总耗时

官方 v0.8.2 没有对应的中文日志增强，继续保留我们的实现。

### 方案对比

| 维度 | v0.8.0 修改版（固定 5 分钟） | v0.8.2 修改版（动态超时） |
|------|---------------------------|------------------------|
| 小文件（<10MB） | 5 分钟 | 5 分钟（相同） |
| 100MB 文件 | 5 分钟（可能不够） | 10 分钟 |
| 200MB 文件 | 5 分钟（不够） | 20 分钟 |
| 覆盖范围 | 仅知识文件上传 | 所有 `postUpload` 调用 |
| 可扩展性 | 每个接口手动加 | 统一处理，自动生效 |

## 二、调试版本优化（不属于版本升级内容）

> 以下优化是针对本地调试环境（pg-fqx 分支）的工程化改进，不属于 v0.8.0 → v0.8.2 的版本升级内容，也不需要同步到生产版本。

### 2.1 调试版前端端口默认值修复

**问题**：`scripts/dev-frontend-nohup.sh` 中默认端口是 `5173`，但 `vite.config.ts` 中调试版前端端口是 `5174`。stop 函数清理端口占用时，会误杀 5173 端口上运行的生产版前端进程。

**修复**：将脚本默认端口从 `5173` 改为 `5174`。

```diff
- FRONTEND_PORT="${DEV_FRONTEND_PORT:-5173}"
+ FRONTEND_PORT="${DEV_FRONTEND_PORT:-5174}"
```

**影响文件**：`scripts/dev-frontend-nohup.sh`（1 行修改）

---

### 2.2 调试版共享文件存储（解决 DOCREADER_PARSE_FAILED）

**问题**：调试版和正式版共用 Redis 基础设施，docreader 解析任务（asynq 队列）可能被任意一方的 worker 抢走。由于两边文件存储在各自的 `.local-data/files` 目录下，任务被对方抢走后找不到文件，报错 `DOCREADER_PARSE_FAILED: failed to get file`。

**根因**：不是 docreader 容器读不到文件，而是**后端 worker 读不到文件**。后端在调用 docreader 之前会自己先调用 `GetFile` 读文件，读到内容后再通过 gRPC 传给 docreader。如果任务被对方 worker 抢到，对方本地没有对应文件就会失败。

**解决方案**：两边共用正式版的文件存储目录。

在调试版创建 `.env.local`（已被 `.gitignore` 忽略）：
```bash
LOCAL_STORAGE_BASE_DIR=/root/home/workspace_cribc/my_weknora/WeKnora/.local-data/files
```

调试版 `dev-app-nohup.sh` 脚本逻辑：若 `LOCAL_STORAGE_BASE_DIR` 为空或等于默认值 `/data/files`，则使用 `$PROJECT_ROOT/.local-data/files`；否则直接使用设置的值。因此设置一个非默认路径即可生效。

**效果**：
- ✅ 调试版上传的文件直接存到正式版目录
- ✅ 不管解析任务被哪边 worker 抢走，都能找到文件
- ✅ 文件名是 UUID，不会冲突
- ⚠️ 调试版删除文件会影响正式版（不建议在调试版做删除操作）

**影响文件**：无源码修改，仅新增本地配置文件 `.env.local`（不提交 git）

---

### 2.3 调试版 Redis DB 隔离（彻底解决任务争抢）

**问题**：共享文件存储只解决了"找不到文件"的问题，但任务队列还是同一个——调试版和正式版的 worker 仍然会互相抢任务。这导致：
1. 测试结果不稳定（同一个文档上传，有时候被新代码处理，有时候被旧代码处理）
2. 调试版的改动可能影响正式版的任务处理（如果新代码有 bug）

**根因**：两个版本都用默认的 Redis DB 0，asynq 任务队列、分布式锁、限流等全部共用。

**解决方案**：利用 Redis 的多 database 特性，让调试版用 DB 1，正式版保持默认 DB 0。

代码本身已经支持 `REDIS_DB` 环境变量（`initRedisClient` 和 `getAsynqRedisClientOpt` 都会读取），不需要改任何代码，只需要在调试版的 `.env.local` 中加一行：

```bash
REDIS_DB=1
```

**效果**：
- ✅ 任务队列完全隔离，两边互不干扰
- ✅ 分布式锁、限流、缓存等全部隔离
- ✅ 零代码改动，纯配置
- ✅ 不影响正式版本，git 安全

**注意**：文件存储共享（`LOCAL_STORAGE_BASE_DIR`）仍然需要保留，因为 docreader 容器是同一个，需要从同一个目录读文件。Redis 隔离和文件存储共享不矛盾：任务各跑各的，但文件都在一个地方。

**影响文件**：无源码修改，仅修改本地配置文件 `.env.local`（不提交 git）

## 三、Wiki 法规场景本体自动化提取（新增 ✅）

### 3.1 背景与目标

**为什么做这个功能？**

之前的 Wiki 系统只有一套**通用提取模式**：从文档中自动提取实体类和概念，LLM 动态规划分类目录。这套方案适合通用知识库，但面对**法规类文档**时有几个痛点：

1. **结构不稳定**：LLM 每次提取的实体粒度不一样，目录划分也不一样，法规类知识需要更稳定的结构
2. **缺少法规专项结构**：法规文档有明确的"法规 → 条款 → 业务对象"三层结构，通用提取抓不住这个主线
3. **关系不准确**：通用关系抽取是 LLM 判断的，而法规里"条款属于哪部法规"这种关系是确定的，不需要 LLM 猜

**解决方案：双体系并行提取**

同一个 Wiki 摄入任务里同时跑两套提取：

| 体系 | 提取内容 | 目录方式 | 适用场景 |
|------|---------|---------|---------|
| **体系A（法规专项）** | 法规详情页 + 精简摘要页 + 条款 + 业务对象 | 规则式固定目录（法规/条款/业务对象） | 法规类文档的核心结构 |
| **体系B（通用提取）** | 实体类 + 概念 | LLM 动态分类目录 | 补充性知识，和原来完全一样 |

通过配置 `WikiConfig.SceneType = "regulation"` 开启法规场景，默认还是 generic（通用模式），**通用场景行为完全不变**。

#### 3.5.4 `internal/application/service/wiki_ingest_batch.go` — 双体系合并

**改动量：大（+301行）**

这是改动最大的文件，核心是在 `mapOneDocument` 中接入双体系提取。

**① newWikiBatchContext 填充 SceneType**

从知识库配置读取 `SceneType`，填入批次上下文。

**② mapOneDocument 双体系提取（核心改动）**

在原有 Pass 0 提取之后、summary 生成之前，插入体系A的提取逻辑：

```
原有逻辑：
  Chunk加载 → Pass 0 候选提取 → summary生成 → chunk引用分类 → 组装updates

法规场景改为：
  Chunk加载 → Pass 0 候选提取（体系B）
            → 体系A提取（法规页面 + 条款/BO）
            → summary生成
            → chunk引用分类（体系A候选合并进来一起分）
            → 引用回填到体系A结果
            → 组装updates（体系A + 体系B，去重）
```

**几个关键设计点：**

1. **chunk 引用分类复用**：把体系A的条款和BO合并到 `candidatesXML` 中，**一起走** `classifyChunkCitations`，然后分别回填。这样体系A的页面也有正确的 chunk 引用，不用重写引用分类逻辑。

2. **双体系去重（体系A优先）**：在组装 Entity 的 update 时，判断 `regSlugItems`（体系A已提取的 slug 集合）是否已包含该 slug，**包含则跳过**体系B的实体。保证同一个实体只保留体系A的版本（法规专项提取更专业）。

3. **法规详情页和精简摘要页**：作为独立的 update 追加到 `updates` 中，和体系B的页面并列。

**③ reduceSlugUpdates 模板路由**

按页面类型选择编辑模板：
- 法规详情页（`entity/regulation-`）：直接覆盖（不走 LLM 合并）
- 条款页（`entity/clause-`）：`WikiRegulationClauseModifyPrompt`
- 业务对象页：`WikiRegulationBusinessObjectModifyPrompt`
- 通用实体/概念：`WikiPageModifyUserPrompt`（原模板，不变）

> **为什么法规详情页直接覆盖？** 因为每篇文档对应一部法规，通常只有一个来源，走 LLM 合并反而可能把内容改坏。和 summary 页面的处理方式类似。

**④ rebuildIndexPage 调用传入 SceneType**

从批次上下文中传递场景类型给索引页重建函数。

### 3.6 设计决策汇总

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 双体系架构 | 同一任务内并行，合并到 slugUpdates | 复用现有 Map-Reduce 框架，改动最小 |
| 体系A优先 | 同名实体跳过体系B | 法规专项提取更专业，质量更高 |
| from_document 关系 | 确定性生成（从 out_links 推导） | 条款→法规的关系是确定的，不需要 LLM 判断，节省 token |
| 三个固定目录 | 保留词 + LLM prompt 注入约束 | 保证目录结构稳定，不与通用目录冲突 |
| 法规详情页 reduce | 直接覆盖，不走 LLM | 单文档单法规，合并无意义且可能引入偏差 |
| chunk 引用分类 | 体系A候选合并进来一起走 | 复用现有逻辑，保证引用一致性 |
| 通用路径 | 零侵入（全部是新增分支） | 零回归风险，generic 场景行为完全不变 |
| 表结构 | 不改表，复用三张表 | v3 已验证可行，改动成本最低 |
| 删除/撤销 | 复用现有 retract 机制 | 基于 SourceRefs 和 out_links，与页面类型无关 |

### 3.7 遇到的问题与处理办法

#### 问题1：buildPreviousSlugsText 函数不存在

**现象**：原计划复用一个公共的 `buildPreviousSlugsText` 函数来构造旧 slug 列表文本，但实际代码中这个函数不存在，各调用处都是内联构造的。

**处理办法**：在 `extractRegulationCandidateSlugs` 函数内**内联构造** `prevSlugsText`，和原代码中其他地方的做法保持一致。没有强行抽公共函数（避免改动面扩大）。

---

#### 问题2：wikiService.UpsertRelations 接口不存在

**现象**：最初设计 `generateFromDocumentRelations` 时计划调用 `wikiService.UpsertRelations` 批量写入关系，但实际 `wikiService` 接口中没有这个方法。

**处理办法**：改为直接用 `s.db` 操作数据库，使用 GORM 的 `Clauses(clause.OnConflict{...}).Create(...)` 实现 upsert。这样虽然绕过了 service 层，但保证了功能可用，且只在这一个新增函数中使用，不影响其他逻辑。

**后续优化建议**：如果后续有更多地方需要批量 upsert 关系，可以考虑在 wikiService 中补充这个方法。

---

#### 问题3：字符串替换失败（缩进/空格不匹配）

**现象**：在修改 `wiki_ingest_batch.go` 等大文件时，多次出现 Edit 工具替换失败，原因是 old_string 中的缩进、空格、换行与实际文件不完全一致。

**处理办法**：每次替换失败后，重新读取文件对应区域获取准确内容，再做替换。对于大文件，分小步、短片段替换，避免一次替换大段代码。

**经验总结**：
- 替换前先 Read 确认精确内容
- 一次替换的代码片段控制在 20 行以内比较稳妥
- 注意 Go 代码中的 tab 缩进和空格区别

---

#### 问题4：函数调用在定义之前（undefined 编译错误）

**现象**：有几处新增的函数调用（如 `selectRegulationModifyPrompt`、`generateFromDocumentRelations`、`planRegulationSceneTaxonomy`）在添加调用之后忘记添加函数定义，导致编译报错 "undefined"。

**处理办法**：编译报错后逐个补充函数定义。这是增量开发中的常见问题，通过 `go build ./...` 及时发现并修复。

**经验总结**：每添加一个新函数的调用，就同步添加函数定义（哪怕是空实现先占位），不要攒到最后。

---

#### 问题5：双体系 chunk 引用分类复用

**现象**：体系A提取的条款和业务对象也需要 chunk 级引用，但 `classifyChunkCitations` 是为体系B设计的。

**处理办法**：将体系A的条款和BO的候选 slug 合并到 `candidatesXML` 中，**一起走** `classifyChunkCitations`，拿到结果后再分别回填到体系A和体系B的结果中。

**好处**：
- 复用了现有引用分类逻辑，不用重写
- 体系A的页面也有正确的 chunk 引用
- 引用的来源是统一的，不会出现偏差

---

#### 问题6：双体系实体去重（体系A优先）

**现象**：体系A提取的业务对象（如"商业养老金"、"个人养老金账户"）很可能也会被体系B（通用实体提取）作为 entity 提取出来，如果两套都生成 update，会导致重复和冲突。

**处理办法**：在组装 Entity 的 update 循环中，判断 `regSlugItems`（体系A已提取的 slug 集合）是否已包含该 slug，**包含则跳过**体系B的实体。

**原则**：体系A优先，同一个实体只保留体系A的版本（法规专项提取更专业）。

---

#### 问题7：法规详情页 reduce 不走 LLM 合并

**现象**：法规详情页是摘要式生成（整文处理），每篇文档对应一部法规，通常只有一个来源。如果走通用的 LLM 编辑合并模板，反而可能把内容改坏。

**处理办法**：在 `reduceSlugUpdates` 的 LLM 调用之前加判断分支：如果是法规详情页（`entity/regulation-` 前缀），直接用最新的 `SummaryBody` 覆盖，不走 LLM 合并。和 summary 页面的处理方式类似。

### 3.9 第一轮测试问题修复

首轮端到端测试后发现并修复了以下三个问题：

#### 问题1："法规"目录为空（0 个页面）

**现象**：上传法规文档后，"法规"目录下没有任何页面，但摘要页和条款/业务对象页面都正常生成了。

**根因分析**：`generateRegulationPages` 一次 LLM 调用需要输出三个 JSON 字段（`detail_content`、`summary_content`、`regulation_meta`），结构复杂导致 LLM 偶尔返回空的 `short_title`。代码中 `if regMeta.ShortTitle != ""` 的守卫判断跳过了详情页创建。

**架构调整**：将法规页面生成从"一次输出三个字段"拆分为两条独立路径：
- **法规详情页**（"法规"目录下，详细版）→ 由 `WikiRegulationPageGenPrompt` 生成，只输出 `detail_content` + `regulation_meta` 两个字段，JSON 结构更简单可靠
- **摘要页**（根目录，精简版）→ 复用现有的通用摘要生成机制，只是在法规场景下切换为 `WikiRegulationSummaryPrompt`（精简版提示词）

**为什么这样更好**：
1. 避免了"两个摘要页面互相打架"的混乱（之前法规提取生成一个、通用机制又生成一个）
2. 减少 JSON 输出字段数，降低 LLM 出错概率
3. 摘要生成走统一路径，后续维护更简单

#### 问题2：空文件夹残留（没有 wiki 页面的目录）

**现象**：LLM 规划的目录中，有些最终没有页面挂入（比如某些实体去重后被丢弃），导致左侧出现空文件夹。

**根因分析**：原有的空目录清理（`PruneEmptyFolderChains`）只在文档撤销（retract）时触发，新增文档时不会主动扫描清理空目录。

**修复方案**：在 finalize 阶段，当有文档新增且 ingest 队列已清空时，自动扫描全量文件夹，把空的目录链一并清理掉。

- 修改文件：`wiki_ingest_batch.go` 的 `ProcessWikiFinalize`
- 改动量：约 15 行，新增一个分支判断
- 影响范围：通用场景同样受益（之前也存在空目录问题）

#### 问题3：三个固定目录没有置顶排序

**现象**：法规/条款/业务对象三个固定目录和通用生成的目录混在一起，按名称拼音排序，没有按照"法规 → 条款 → 业务对象"的顺序置顶排列。

**根因分析**：文件夹创建时 `sort_order` 都是默认值 0，列表查询按 `sort_order ASC, name ASC` 排序，所以所有文件夹同一优先级，按名称拼音混排。

**修复方案**：在 `resolvePlannedFolders` 之后，法规场景下给三个固定顶层目录设置 `sort_order = -3/-2/-1`（负值），确保它们排在所有默认 0 值的目录前面，且按指定顺序排列。

- 修改文件：`wiki_ingest_taxonomy.go`
- 改动量：约 30 行，新增一个 `applyRegulationTopFolderSortOrder` 函数
- 同时处理新创建的和历史已存在的固定目录

### 3.10 第二轮测试问题修复

第二轮测试（ceshi2 知识库，6 份保险监管法规文档）发现并修复了以下两个 bug，同时排查了一个环境问题。

#### 问题4：法规详情页没有写入数据库（法规目录 0 页面）

**现象**：法规目录下页面数量为 0，但日志显示法规页面生成成功、`short_title` 也有值。摘要页、条款、业务对象都正常。

**根因分析**：`reduceSlugUpdates` 函数中，法规详情页的分支在设置完 `page.Content`、`page.Title` 等字段后，直接 `return changed, affectedType, false, nil`，**跳过了后面的 folder_id 分配和 CreatePage/UpdatePage 保存逻辑**。

这是一个典型的"提前 return 漏写数据库"bug。其他页面类型（条款、业务对象、通用实体）都走了 `savePage` 标签后的统一保存逻辑，只有法规详情页分支提前返回了。

**修复方案**：将法规详情页分支的 `return` 改为 `goto savePage`，跳到函数末尾的统一保存逻辑，和其他页面类型走同一条路径。

- 修改文件：`internal/application/service/wiki_ingest_batch.go`
- 改动量：1 行（`return` → `goto savePage`）+ 在函数开头加 `savePage:` label
- 关键代码位置：`reduceSlugUpdates` 函数内的法规详情页分支

> **经验教训**：在有多条 return 路径的函数中新增分支时，一定要确认每条路径是否覆盖了所有必要的收尾逻辑（如保存、清理、日志等）。最好使用统一的出口标签（如 `savePage:`）来避免遗漏。

#### 问题5：摘要页"查看完整法规详情"链接无法跳转

**现象**：摘要页底部有"👉 **查看完整法规详情**"链接，但点击后无法跳转到对应的法规详情页。

**根因分析**：提示词 `WikiRegulationSummaryPrompt` 中生成跳转链接时，用了 **Markdown 链接格式** `[查看完整法规详情](entity/regulation-xxx)`。但 Wiki 系统的内部链接识别用的是 **Wiki 链接格式** `[[slug|显示文本]]`，Markdown 格式的链接不会被识别为内部跳转。

**修复方案**：修改提示词中的链接格式，从 markdown 改为 wiki 内部链接格式。

```diff
- 👉 **[查看完整法规详情](entity/regulation-<short_title>)**
+ 👉 **[[entity/regulation-<short_title>|查看完整法规详情]]**
```

- 修改文件：`internal/agent/prompts_wiki.go`
- 改动量：1 行
- 涉及提示词：`WikiRegulationSummaryPrompt`

> **经验教训**：Wiki 系统内部链接统一使用 `[[slug|display_text]]` 格式，不要用 markdown 的 `[text](url)` 格式。前者会被前端识别为内部路由跳转，后者只会被当作普通链接处理。

### 3.11 环境隔离问题排查与解决方案

#### 现象

第二轮测试时发现：新创建的 ceshi2 知识库上传文档后，没有生成法规/条款/业务对象三个固定目录，全部是通用模式的结果。但之前的"测试"知识库又能正常生成体系A的结果。

#### 排查过程

1. 检查代码确认 scene_type 默认值已改为 regulation，没问题
2. 检查日志发现 ceshi2 的 wiki 任务显示 "6 rows held by fresh claims"，说明任务被其他 worker claim 了
3. 检查进程发现有两个 server 进程都在连同一个 dev Redis：
   - PID 3774637（10月8日启动，旧代码，PPID=1 孤儿进程）
   - PID 662351（10月10日启动，新代码，当前 dev 服务）
4. 两个进程都在消费同一个 wiki 任务队列，任务随机分配。ceshi2 的任务刚好被旧代码的 worker 抢到了

#### 根因

`my_weknora/Weknora`（"正式版"dev 模式）和 `fqx_weknora/WeKnora`（调试版）**连的是同一个 dev Redis 实例（127.0.0.1:16379），用的都是默认 DB 0**。两个后端都在消费同一个 asynq 任务队列，任务随机分配给两边的 worker。

之前能跑对是因为任务刚好被新代码的 worker 抢到了，属于概率事件。

#### 解决方案：使用不同的 Redis DB 隔离

代码已经支持 `REDIS_DB` 环境变量（`initRedisClient` 和 `getAsynqRedisClientOpt` 都会读取），默认值为 0。

在调试版的 `.env.local` 中设置 `REDIS_DB=1`，让调试版使用 Redis DB 1，与正式版（DB 0）完全隔离：

```bash
# .env.local（已被 .gitignore 忽略，不提交 git）
REDIS_DB=1
```

**效果**：
- ✅ 两个版本的任务队列完全隔离，不会互相抢任务
- ✅ 两个版本的分布式锁、限流、缓存等也完全隔离
- ✅ 零代码改动，只改本地配置
- ✅ 不影响正式版本，git 提交安全

> **注意**：文件存储目录的共享配置（`LOCAL_STORAGE_BASE_DIR`）需要保留，因为 docreader 容器是同一个。Redis 隔离和文件存储共享不矛盾——任务队列隔离了，但两边上传的文件都存在同一个目录，docreader 都能读到。

#### 优化 2：法规页面 JSON 解析失败重试机制

**问题**：`generateRegulationPages` 调用 LLM 生成法规页面时，偶尔会出现 JSON 解析失败，错误信息为 `invalid character '}' after top-level value`——LLM 在合法 JSON 后输出了额外的解释文字，导致 `json.Unmarshal` 失败。

**修复方案**：双重保障

1. **`extractFirstJSONObject` 函数**：用括号匹配法从字符串中提取第一个完整的 JSON 对象，忽略 JSON 前后的多余文字。即使 LLM 输出了"好的，这是结果：{...} 如果你需要... "也能正确提取。
2. **最多 3 次重试**：每次失败后重新调用 LLM，共 `maxAttempts = 3` 次，降低单次失败概率。

- 修改文件：`internal/application/service/wiki_ingest_cite.go`
- 新增函数：`extractFirstJSONObject`（括号匹配提取首个 JSON）
- 修改函数：`generateRegulationPages`（增加重试循环）
- 改动量：约 50 行

**为什么不用正则？** 因为 JSON 嵌套结构复杂，正则无法正确处理嵌套的大括号和字符串中的转义括号。括号匹配法（深度计数 + 字符串状态判断）是最可靠的方案。

#### 优化 6：LLM 条款页质量审核（Finalize 阶段质检）

**问题**：Map 阶段的字数过滤和 prompt 强化还是不够——有些页面字数够了但内容空洞（全是套话），有些来源信息是占位文字，硬规则抓不住。

**解决方案**：在 **Finalize 阶段**增加一步 LLM 质检，批量检查条款页面质量，删除无效页面。

**设计**：
- **触发时机**：Finalize 阶段，关系生成之后、空目录清理之前（删除页面可能产生空目录，由后续 prune 处理）
- **检查范围**：只针对 `entity/clause-*` 前缀的条款页，其他类型页面不检查
- **分批处理**：每批 20 个页面，控制单次 LLM 调用的 token 量
- **保守策略**：解析失败的批次不删除（宁留勿删），只删明确判定为无效的

**有效性判断标准**（满足任意一条即为无效）：
1. 内容空洞：字数太少或无实质监管内容
2. 占位文字多：包含"待定/待补充/暂无/待关联"等且无实质内容
3. 缺少来源：没有来源法规或来源信息明显错误
4. 无独立意义：只是其他条款的片段复述
5. 几乎空白：只有标题或寥寥数语

**新增提示词**：`WikiClauseQualityCheckPrompt`
- 输入：一批条款页的 slug + 标题 + 内容（每页面截断 2000 字符）
- 输出：JSON 数组，每个元素 `{ slug, is_valid, reason }`
- 支持 `extractFirstJSONArray` 容错提取（与 `extractFirstJSONObject` 配对）

**新增函数**：`checkClausePageQuality`
- 加载页面完整内容 → 分批调用 LLM → 解析结果 → 删除无效页 → 返回被删 slug 列表
- 删除后再跑一次死链清理（被删页面可能导致其他页面出现死链）

- 修改文件：
  - `internal/agent/prompts_wiki.go`（新增 `WikiClauseQualityCheckPrompt`，约 60 行）
  - `internal/application/service/wiki_ingest_cite.go`（新增质检函数 + JSON 数组提取，约 160 行）
  - `internal/application/service/wiki_ingest_batch.go`（finalize 阶段接入，约 15 行）

### 3.14 法规场景图片描述补齐（v0.8.3 对齐补充）

#### 背景

通用页面（entity/concept/summary）的切块图片信息（caption / OCR / 图片 URL）在 Wiki 摄入链路里已经有完整的富化机制：`searchutil.EnrichContentWithImageInfo` 把切块里的图片包成 `<image url="..."><image_caption>...</image_caption><image_ocr>...</image_ocr></image>` XML 块喂给 LLM，通用 prompt 里也明确写了"图片规则"，要求 LLM 把相关图用 `![caption](url)` Markdown 语法抄到页面里。

但法规场景的 4 个二开 prompt（`WikiRegulationPageGenPrompt` / `WikiRegulationExtractPrompt` / `WikiRegulationClauseModifyPrompt` / `WikiRegulationBusinessObjectModifyPrompt`）有两个洞：

1. **模板变量没接线**：条款页/业务对象页编辑模板引用了 `{{.NewMaterial}}` 和 `{{.SourceContext}}`，但 Reduce 调用点 `wiki_ingest_batch.go:reduceSlugUpdates` 构造 template data map 时只填了通用 prompt 用的 `NewContent` / `SharedSourceContexts`，没填这两个 key。Go `text/template` 对缺失 map key 渲染成 `<no value>`，导致**条款页/业务对象页编辑 LLM 实际看不到源切块内容**（包括 `<image>` 图片 XML）。
2. **prompt 没图片规则**：4 个法规 prompt 里完全没有 image/caption/OCR 字样，LLM 即使看到了 `<image>` 块也不知道要不要抄、怎么抄。

#### 修复（最小改动，不动二开结构）

**文件 1：`internal/application/service/wiki_ingest_batch.go`**

在 `reduceSlugUpdates` 的 template data map 末尾追加两个 key，值复用同一份富化后切块内容：

```go
// 法规场景的条款页/业务对象页编辑模板使用 {{.NewMaterial}} 与
// {{.SourceContext}} 变量，与通用 WikiPageModifyUserPrompt 的
// NewContent / SharedSourceContexts 是同一份富化后的切块内容
// （含 <image> 图片 XML）。这里同名透传，避免模板渲染成 <no value>。
"NewMaterial":   newContentBuilder.String(),
"SourceContext": sharedSourceContexts.String(),
```

通用 prompt 不读这两个 key，多两个 map 项零影响。

**文件 2：`internal/agent/prompts_wiki.go`**

给 4 个法规 prompt 各追加一条图片规则，措辞照通用 prompt 第 103/183/193/461 行的写法：

| Prompt | 规则位置 | 要求 |
|--------|---------|------|
| `WikiRegulationPageGenPrompt` | Wiki 链接规则之后 | 详情页相关图（流程图/架构图/表格截图）插入 `detail_content` |
| `WikiRegulationExtractPrompt` | 六、注意事项第 3 条 | 提取阶段 details 末尾可带相关图 |
| `WikiRegulationClauseModifyPrompt` | 重要规则第 8 条 | 只从 `<new_material>` 取图，URL 原封不动当不透明令牌 |
| `WikiRegulationBusinessObjectModifyPrompt` | 更新规则第 7 条 | BO 结构示意图/指标体系表可插入 |

统一规则要点：
- URL 是不透明令牌，必须原封不动精确复制，不能修改/缩短/标准化
- 纯装饰性图片（印章、页眉页脚、扫描件边框、无实质信息截图）不插入
- 新来源材料中没有相关图片时，不要编造链接，也不要把现有页面中无关图片保留下来

| 验证点 | 结果 |
|--------|------|
| 后端加载新 prompt | 日志中出现"7. 图片规则"/"8. 图片规则"中文段落 |
| `NewMaterial` 接线 | `<new_material>` 块渲染出真实切块内容（含 `<image url="...">` XML），不再是 `<no value>` |

## 四、智能体检索工具统一升级（已完成 ✅）

### 4.1 背景

v0.8.0 中知识库检索相关的 Agent 工具有 4 个：

| 工具名 | 用途 |
|--------|------|

v0.8.2 官方将这 4 个工具**合并精简为 3 个统一工具**，功能更聚合、接口更一致：

### 9.2 Wiki 页面续写机制

**文件**：
- `internal/agent/prompts_wiki.go`（新增 `WikiPageModifyContinuationPrompt`）
- `internal/application/service/wiki_ingest.go`（续写核心逻辑）

#### 背景

Wiki 页面改写（`WikiPageModifyUserPrompt` 及其法规变体）是所有 LLM 调用中输出最长的一个。当页面内容很多、或者 `wikiLLMMaxTokens` 不足以装下完整页面时，LLM 输出会被拦腰截断（`finish_reason=length`），导致：
1. 页面结构不完整（可能正写在表格行中间就断了）
2. 内容被部分覆盖保存，下次合并时基于残缺内容继续，越合越坏
3. 用户看到的是一个半成品页面

v0.8.2 官方新增了**页面续写机制**：检测到输出被截断时，自动追加续写提示词让 LLM 从中断处继续，最多 3 轮，写不完则报错拒绝写回。

#### 实现要点

**① 续写触发条件**

- 仅对**页面改写类 prompt** 生效（`WikiPageModifyUserPrompt` + 法规条款/业务对象变体）
- 触发条件：`finish_reason` 为 `length` / `max_tokens` / `max_output_tokens`（归一化到 `isLengthStopFinishReason` 函数判断）
- 其他 prompt（JSON 提取类、摘要、去重等）**不触发续写**——这些输出长度可控，不需要

**② 续写流程**

```
第 0 轮：初始调用（走 singleflight + warmup + 重试）
  ├─ finish_reason != length → 直接返回
  └─ finish_reason == length → 进入续写循环
       ┌───────────────────────────────────┐
       │ 第 1 轮续写：                      │
       │   追加 assistant(部分页面)        │
       │   + user(continuation prompt)    │
       │   调用 LLM（纯重试，不走缓存）    │
       │   ├─ 回复 "(complete)" → 写完了   │
       │   ├─ finish_reason != length → 返回│
       │   └─ 仍被截断 → 下一轮             │
       └───────────────┬───────────────────┘
                       ▼
              最多 3 轮续写
                       │
                       └─ 仍被截断 → 返回 errWikiPageRewriteTruncated
                          （调用方应丢弃本次部分结果）
```

**③ 哨兵机制**

模型回复恰好为 `(complete)`（忽略大小写和首尾空白）时，视为页面已写完。
- 哨兵字符串**不追加到页面内容中**
- `finish_reason` 置为 `"stop"`，视为正常完成

**④ 安全兜底**

用尽所有续写轮次（默认 3 轮）后仍然被截断 → 返回 `errWikiPageRewriteTruncated` 错误。
- **拒绝写回残缺页**——写回一个不完整的页面比写失败更糟（下次合并会基于残缺内容）
- 调用方（reduceSlugUpdates）收到错误后，该页面的更新失败，不会覆盖现有页面

**⑤ 架构分层（清晰解耦）**

| 层级 | 函数 | 职责 |
|------|------|------|
| 对外接口 | `generateWithTemplate` | 返回 `(string, error)`，与原有签名完全一致，所有调用方零改动 |
| 增强版 | `generateWithTemplateResult` | 返回 `wikiLLMResult{Content, FinishReason}`，内含续写循环 |
| 带缓存调用 | `callWikiLLMOnce` | 单次调用，含 warmup + singleflight + 重试（初始第 0 轮用） |
| 纯重试调用 | `callWikiLLMRetryOnly` | 单次调用，只含重试（续写轮次用，不走缓存） |
| 最内层 | `chatWithRetry` | 纯 LLM 调用 + 指数退避重试，被以上两层共用 |

#### 对外接口零改动

`generateWithTemplate` 的签名保持 `(string, error)` 不变，所有现有调用方（约 10+ 处）完全不需要修改。续写逻辑自动对页面改写场景生效，其他场景行为完全不变。

### 9.3 Wiki 同名页面跨类型复用（issue #3526）

#### 背景

LLM 在多次摄入中对同一事物的类型判断会漂移——第一次可能判定为 `concept`（概念），第二次又判定为 `entity`（实体），导致知识库中出现 `concept/孔子` 和 `entity/孔子` 两个孪生页面，内容重复且结构混乱。

v0.8.2 官方版在确定性去重（exact identity）路径上增加了**跨类型复用**机制：同类型找不到同名页面时，自动回退到跨类型（entity ↔ concept）查找，复用已有页面。

#### 核心设计

**1. 标题归一化（identity key）**

`normalizeWikiIdentityTitle()` 将页面标题归一化为身份键：
- 去除所有空白字符（空格、制表符、换行、全角空格等）
- 统一转为小写
- **保留标点符号**（如 "寓言" ≠ "《寓言》"，避免把概念和作品章节混淆）

**2. 跨类型复用决策（exactIdentityTarget）**

```
新条目 (名称=孔子, 类型=entity)
  │
  ├─ 查找同类型 (entity) 下同归一化标题的已有页面
  │     ├─ 找到 → 直接复用（同类型优先）
  │     └─ 未找到 → 进入跨类型回退
  │
  └─ 查找跨类型 (concept) 下同归一化标题的已有页面
        ├─ 找到 → 复用该页面（即使类型前缀不同）
        └─ 未找到 → 保留原 slug，新建页面
```

关键规则：
- **同类型优先**：有同类型同名页面时，绝不跨类型复用
- **仅适用于 entity ↔ concept**：summary、index、synthesis、comparison 等页面类型不参与
- **下游写入以 slug 为键**：复用后新内容写入已有页面（沿用其类型前缀），孪生页面永远不会形成

**3. 三重收敛保障**

| 层级 | 机制 | 位置 |
|------|------|------|
| 第一层 | 同批次精确身份绑定（attachExactIdentityPages 跨类型安全网） | trigram 相似度探测之外，显式按归一化标题查询同类型和跨类型页面 |
| 第二层 | 跨批次身份声明（claimWikiIdentitySlug） | Redis 原子性预留 slug，并发批次收敛到同一 slug |
| 第三层 | 引用发现后回收（reclaimExtractedIdentities） | citation 阶段产生的新 slug 再跑一轮精确匹配，防止引用路径产生孪生 |

#### 移植改动

**文件**：`internal/application/service/wiki_ingest_dedup.go`（修改）

| 函数 | 改动 | 行数 |
|------|------|------|
| `normalizeWikiIdentityTitle` | 更新注释（说明跨类型用途） | 注释 |
| `exactIdentityTarget` | 新增 `crossMatches` 分支 + 跨类型兜底返回 | +10 行 |
| `otherWikiPageType` | 新增工具函数（entity ↔ concept 互换） | +6 行 |
| `attachExactIdentityPages` | 末尾新增跨类型安全网查询（带缓存） | +60 行 |

**总新增代码**：约 76 行

**涉及调用点**：0 处（函数签名不变，现有调用方自动生效）

**数据库变更**：0 个（复用已有 `wiki_pages` 表和索引）

#### 与二次开发的兼容性

- ✅ **L1/L2 两层本体**：无冲突。跨类型复用只在 entity/concept 页面类型之间生效，与 L1/L2 抽取粒度是正交维度
- ✅ **法规场景双体系**：无冲突。体系A全是 entity 类型，同类型匹配优先；体系B的 entity/concept 受益于跨类型复用
- ✅ **关系抽取**：无冲突。关系抽取在 finalize 阶段运行，不涉及去重逻辑
- ✅ **LLM 语义去重（dedupMergeRejectReason）**：两条路径互不干扰。LLM 提议的跨类型合并仍然被拒绝，只有 exact title match 才允许跨类型——这是设计有意为之的安全边界

### 9.4 Wiki 引用片段包含图片描述

#### 背景

<image_caption>图片描述</image_caption>
<image_ocr>OCR 文本</image_ocr>
</image>

### 9.5 Wiki 跨 KB 搜索

### 9.6 Wiki 摄入 panic 恢复

#### 背景

v0.8.0 修改版中，Wiki 摄入流程如果某个文档或某个页面的处理发生 panic（空指针、数组越界等），会导致整个 asynq worker 进程崩溃。errgroup 不会自动 recover panic，一个坏文档就能拖垮整个批次。

v0.8.2 官方在两个关键位置增加了 panic 恢复：**Map 阶段**和 **Reduce 阶段**，将 panic 转为普通 error，保证单个失败不影响其他文档/页面的处理。

#### 核心设计

**Map 阶段恢复**（`mapOneDocumentRecovered`）
- 包装 `mapOneDocument` 函数，defer recover 捕获 panic
- panic 时记录错误日志（含文档 ID + panic 信息 + 堆栈）
- 返回 `nil, nil, fmt.Errorf("wiki map panicked: %v", r)`
- 上层将其计入 `ingestFailed`，走失败重试预算，最坏情况进入死信队列

**Reduce 阶段恢复**（`withSlugLock` 回调内）
- 在每个 slug 的 reduce 回调中加 defer recover
- panic 时记录错误日志（含 slug + panic 信息 + 堆栈）
- 将 `reduceErr` 设为 panic error
- 上层将失败的 slug 重新入队，走失败重试预算

#### 迁移改动

| 路径 | 改动类型 | 说明 |
|------|---------|------|
| `internal/application/service/wiki_ingest_batch.go` | 新增包装函数 | `mapOneDocumentRecovered`（约 20 行） |
| `internal/application/service/wiki_ingest_batch.go` | Reduce 回调增强 | `withSlugLock` 回调内增加 defer/recover |
| `internal/application/service/wiki_ingest_batch.go` | import 新增 | `runtime/debug` |
| `internal/application/service/wiki_ingest_batch.go` | 调用点更新 | Map 阶段调用从 `mapOneDocument` 改为 `mapOneDocumentRecovered` |

#### 兼容性分析

- ✅ **零侵入**：纯新增保护，正常流程行为完全不变
- ✅ **不影响数据一致性**：panic 的文档/页面走失败重试，不会产生半成品数据
- ✅ **L1/L2 本体/关系抽取/法规场景**：无冲突，全部受益于 panic 保护

### 9.7 Wiki follow-up 动态扇出

#### 背景

v0.8.0 修改版中，Wiki 摄入的 follow-up 调度是单任务模式：每个批次处理完后，不管积压多少文档，都只调度一个 follow-up 任务。在文档大量上传时，吞吐量受限于单批次处理速度。

v0.8.2 官方实现了**动态扇出**机制：根据当前待处理文档数量和可用并发槽位，动态决定启动多少个 follow-up 任务。大积压时自动增加并发，小流量时保持单任务，既提速又不浪费资源。

#### 核心设计

**动态调度公式**（`followUpTriggerCount`）
```
batchesNeeded = ceil(pending / batchSize)   // 需要多少批次
freeSlots = maxInflight - activeSlots + 1   // 可用槽位（+1 允许当前批次预定接班人）
n = min(batchesNeeded, freeSlots)            // 启动 n 个 follow-up
```

**Redis 信号量控制**（`reserveFollowUpTasks`）
- 用 Redis ZSET 维护每个 KB 的 follow-up 预留池
- 原子 Lua 脚本：`ZCARD` 计数 + `ZADD` 预留，保证并发安全
- 上限：`maxInflight + 1`（多一个允许交接班）
- 每个预留带过期时间（2 分钟），防止入队失败或 worker 崩溃导致泄漏

**对账机制**（`reconcileFollowUpTasks`）
- 定期检查过期预留，与 asynq 实际任务状态对比
- 任务已完成/归档 → 移除预留
- 任务仍在运行 → 续期
- 确保预留池状态与实际队列一致

**兜底探针**（`scheduleFollowUpRecheck`）
- 所有容量被占满但入队失败时，安排一个合并的探针任务
- 每个 KB 最多 2 个探针（交替 ID），不会产生惊群效应
- 保证极端情况下进度不会卡死

**远期兜底**（`scheduleStaleClaimRecheck`）
- ClaimBatch 拿不到任何行（全被新鲜认领占着）时，安排一个远期重检
- 延迟 = `wikiClaimStaleAfter + wikiFollowUpDelay`（约 90 分钟后）
- 用于处理认领者崩溃导致行被锁住的情况

**函数清单**（新增 `wiki_ingest_followup.go`）
| 函数 | 职责 |
|------|------|
| `followUpTriggerCount` | 计算应该启动多少个 follow-up |
| `reserveFollowUpTasks` | Redis 原子预留 follow-up 槽位 |
| `reconcileFollowUpTasks` | 对账：与 asynq 实际状态同步 |
| `releaseFollowUpTask` | 释放当前任务的 follow-up 预留 |
| `scheduleFollowUpRecheck` | 安排合并式兜底探针 |
| `activeInflightSlots` | 统计当前活跃 in-flight 槽位数（新增于 wiki_ingest.go） |
| `ClaimableCount` | 统计可认领的不同文档数（新增于 task_queue.go） |

#### 迁移改动

| 路径 | 改动类型 | 说明 |
|------|---------|------|
| `internal/types/interfaces/task_queue.go` | 接口新增 | `TaskPendingOpsClaimableCounter` + `ClaimableCount` |
| `internal/application/repository/task_queue.go` | 实现新增 | `ClaimableCount` 可认领文档计数 |
| `internal/application/service/wiki_ingest.go` | 新增函数 | `wikiInflightCountScript` + `activeInflightSlots` |
| `internal/application/service/wiki_ingest_followup.go` | 新增文件 | follow-up 预留/对账/重检/动态调度 |

- ✅ **向后兼容**：Lite 模式（无 Redis）自动回退到单 follow-up，行为与之前一致
- ✅ **不影响数据一致性**：只是并发度调整，每个文档的处理流程不变
- ✅ **L1/L2 本体/关系抽取/法规场景**：无冲突，全部受益于并发提升
- ✅ **限流保护**：触发上游限流时自动退回单 follow-up，避免放大 429 风暴
