## 〇、大白话

先用人话说结论：**新写一个独立的 Python 小程序（"侧车"，跟 WeKnora 主程序并排跑但各过各的），对外它是唯一的 MCP 服务，对内它只用 WeKnora 早就公开的 HTTP 接口办事，不碰 WeKnora 内部代码。** 这样以后 WeKnora 再升级，内部怎么大改都跟它没关系——就像你家换了厨房，外卖员还是走小区大门，大门这十年没换过。

- 客户端只需要填**一个网址、一个密钥**，不用再配两个头；
- 不带用户身份的密钥（Claude Desktop 这类）能用，带用户身份的密钥（千机/OpenCode 网关签的）也能用，同一个网址、同一把钥匙自动识别——**有票就是用户、没票就是机器，不用再维护"哪些端点要票"的名单**；
- 侧车 v1 只做**只读 9 个工具**（检索 5 个 + 问答 1 个 + wiki 3 个），不做任何写库操作；工具名字参数照旧，OpenCode 的提问习惯不用改；
- **数据库一个字段都不加，也不需要任何身份配置文件**：端点开放的"公共书架"任何机器和用户都能看，用户自己的库凭票据取个人授权，两份书单**取并集、自动去重**；公共书架留空时机器一个库都看不到；
- 千机网关现在签票据的逻辑基本不用动，只是把票据从"第二个头"挪到密钥后面拼一下；
- 我们核对了 0.8.0 到 0.9.0 四个版本，这 12 个工具要走的 HTTP 接口**全部都在、路径没变、只有新增没有删除**（唯一一个删掉的接口我们不用）。

## 一、结论（建议拍板项）

1. **新建独立 Python 侧车 `mcp-sidecar/`**（不覆盖、不改动官方遗留在 `mcp-server/` 的旧 Python 包），官方 `mcp` Python SDK 2.3.x，Streamable HTTP **无状态**传输（与内置 Go MCP 同档）。
2. **侧车对 WeKnora 后端只走 REST（/api/v1，X-API-Key）**，不 import Go 内部接口；读两张配置表（`mcp_endpoints`、`mcp_user_permission`）只做只读直连，且只 SELECT 固定列名。
3. **对外单 URL（`http://<host>:<port>/mcp`）+ 单 Bearer**，端点身份从令牌本身识别，路径里不再带 endpoint_id。Bearer 两种形态：
   - `mcp_xxx`：机器凭证（不区分用户的客户端）；
   - `mcp_xxx.<JWT>`：复合凭证（区分用户的客户端，JWT 就是现有千机网关已在签发的那张票）。
4. **v1 工具面为只读 9 个**（list_knowledge_bases / search_knowledge / grep_chunks / list_documents / read_document / ask / wiki_search / wiki_read_page / wiki_index），同名同参契约冻结；不做 add/update/delete 任何写库操作（下载原始文件留 v1.1）。内部 REST 返回形状由侧车统一转换，REST 变化只改每个工具一个适配函数。
5. 内置 Go MCP **先并存不删**，客户端灰度切完后再通过配置下线；Go 侧代码一行不改。
6. **零数据库迁移、零身份配置文件**：不加列、不建表，PG/SQLite 版本号都不动。机器/用户模式不做端点级配置，由请求凭证现场自识别（2026-11-03 修订，见 §4.2、§七、§十三 7）。

## 二、调研事实

### 2.1 官方 Python MCP 是什么路子（已逐行读源码）

源码位置：`指南/变更文档/版本/源码/WeKnora-0.9.0/mcp-server/weknora_mcp_server.py`（1230 行）。

- 架构就是 **独立进程 + `requests` 调 WeKnora REST + 装饰器注册 MCP 工具**，没有任何对 Go 内部包的依赖。工具函数里基本只做两件事：调 REST、把 dict 直接返回（框架自动序列化）。
- 网络传输由 SDK 给出一个 **Starlette ASGI 应用**，外面套一层自写的 `MCPAuthMiddleware` 做 Bearer 共享密钥鉴权（secrets.compare_digest 常量时间比较），再用 uvicorn 启动。stdio/sse/http 三种传输可选，http 为 Streamable HTTP、stateless。
- 它的历史包袱（31 个工具杂、租户管理/模型管理都往里塞、SSE 手搓解析）我们**不继承**，只继承"侧车 + REST 适配"这个骨架。

**你想借鉴的这套逻辑，事实成立，可以直接用。**

### 2.2 Python MCP 框架选型（PyPI 实时核实，非凭印象）

| 候选 | 实测版本/日期 | 结论 |
|---|---|---|
| 官方 SDK `mcp` | **2.3.0（2026-10-02）**，要求 Python ≥3.10 | **选用**。旧 `FastMCP` 类 2.0 起更名 `MCPServer`（`from mcp.server import MCPServer`），仍是装饰器注册、类型注解决定 JSON Schema；`streamable_http_app(stateless_http=True, max_request_body_size=..., max_sessions=..., transport_security=...)` 返回 Starlette 应用；传输层就是 Starlette/uvicorn |
| 第三方 `fastmcp`（gofastmcp，PrefectHQ） | 4.1.5（2026-11-01），活跃 | 不选。功能多（代理/OpenAI/Gemini 一揽子）但依赖面大（fastmcp-slim + pydantic-settings + rich + platformdirs…），我们只需要一个薄服务端，官方 SDK 足够且与 WeKnora 官方 Python 包同源 |
| FastAPI | —— | **可以用但没必要**。SDK 给的是 Starlette（FastAPI 的底座）应用，鉴权用 ASGI 中间件即可，不需要 FastAPI 的路由/序列化体系。若将来要在同进程加管理接口，外层套一个 `Starlette(routes=[Mount("/mcp",...), Route("/healthz",...)])` 就够，依赖更轻 |

依赖面（官方 SDK 2.3.0 自带）：starlette、uvicorn、pydantic、httpx2、sse-starlette、pyjwt[crypto]、jsonschema。我们额外只需要 **asyncpg**（只读 PG）和 **redis**（限流，复用现有 Redis）。

### 2.3 REST 契约跨版本稳定性证据（回答"换接口影响大不大"）

对 0.8.0 / 0.8.2 / 0.8.3 / 0.9.0 四个官方快照的 `internal/router/` 全量比对 + 当前 pg-fqx 分支核实（v1 只实现只读 9 工具；表中写接口的核对结果保留备查，不进 v1）：

| 我们要用的 REST 接口 | 0.8.0 | 0.8.2 | 0.8.3 | 0.9.0 | 当前分支 |
|---|---|---|---|---|---|
| GET /knowledge-bases（列自有库） | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /shared-knowledge-bases（列共享库，顶层路径） | ✅ | ✅ | ✅ | ✅ | ⚠️ 路由在，但要求 manage_spaces 全权钥匙，retrieve-only 钥匙 403（1-C 实测，见下方修正） |
| POST/GET /knowledge-bases/:id/hybrid-search | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /knowledge-bases/:id/knowledge（文档分页） | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /knowledge/:id（文档详情，**返回体含 `knowledge_base_id`**） | ✅ | ✅ | ✅ | ✅ | ✅ |
| POST .../knowledge/manual、PUT /knowledge/manual/:id | ✅ | ✅ | ✅ | ✅ | ✅ |
| POST .../knowledge/url、.../knowledge/file | ✅ | ✅ | ✅ | ✅ | ✅ |
| DELETE /knowledge/:id | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /chunks/:knowledge_id（分片分页，最大 100） | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /knowledgebase/:kb_id/wiki/search、/pages/*slug、/index | ✅ | ✅ | ✅ | ✅ | ✅ |
| POST /sessions | ✅ | ✅ | ✅ | ✅ | ✅ |
| POST /knowledge-chat/:id、/agent-chat/:id（SSE） | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /agents、/agents/:id | ✅ | ✅ | ✅ | ✅ | ✅ |

- 四个版本间路由**全部是加法**（0.9.0 多了沙箱、浏览器、automation 等，与我们无关）；唯一删除的是 `GET /knowledge-bases/:id/shared-knowledge-bases`（组织维度的变体），顶层 `/shared-knowledge-bases` 四个版本都在（但权限门槛见下方 1-C 修正，侧车实际不调它）。
- 守卫 `KBAccessRead` 走 `middleware.RequireKBAccess(..., kbService, kbShareService, ...)`（[rbac.go:556](internal/router/rbac.go#L556)），**X-API-Key 持有的工作空间对"共享给本空间的库"天然可读**，共享库走 effective tenant 上下文（HybridSearch handler 内显式支持）。
- **【1-C 实测修正】共享库发现路径改道**：`GET /shared-knowledge-bases` 挂的是 `apiKeyManageSpaces(apiKeyFullAccess())`（[routes_agent.go:209](internal/router/routes_agent.go#L209)），retrieve-only 钥匙调它一律 403，不能作为共享库发现入口。侧车改为：① 自有库走 `GET /knowledge-bases`（短缓存 30s）；② 生效范围（公共书架/并集授权，2026-11-03 修订）里的 id 若不在自有列表，**并发逐个 `GET /knowledge-bases/:id` 补详情**——该路由走 `KBAccessRead`，组织共享给本空间的库可读，404/403/5xx 按 Go 既有 warn-and-continue 静默丢弃；③ scope 是闭集，范围外的选择器绝不补查详情（fail-closed）；空范围端点（公共书架与个人授权皆空）直接"无可用知识库"，不再像旧"空=全工作空间"语义那样由 REST 钥匙权限兜底。`KBAccessRead` 对共享库可读的结论不变，只是发现方式从"列表交集"变成"按 id 补详情"。
- 问答 SSE 事件名 `answer / references / complete / error` 在 0.8.0 与 0.9.0 两端都在，未改名。
- **【阶段 2 实测修正】ask 链路的 API Key 能力门控**：原设计假设 v1 纯只读、钥匙只需 retrieve。实测三条路由都挂在 chat 策略上——`POST /sessions`、`POST /knowledge-chat/:id`、`POST /agent-chat/:id` 是 `apiKeyChat(apiKeyFullAccess())`（[routes_chat.go:51](internal/router/routes_chat.go#L51)、[:125](internal/router/routes_chat.go#L125)、[:131](internal/router/routes_chat.go#L131)）；`GET /agents/:id` 是 `apiKeyReadAgents(apiKeyManageAgents(apiKeyChat(apiKeyFullAccess())))` 的 **any-of 允许列表**（[routes_agent.go:26-40](internal/router/routes_agent.go#L26)，[api_key_gate.go:33](internal/middleware/api_key_gate.go#L33) 注释明确 any-of），持 chat 即放行。结论：**开放 ask 的部署，上游钥匙授 retrieve + chat 两项即可，永不授 full access**；侧车请求体仍永不携带 `web_search_enabled`，chat 能力不扩大触网面。不开放 ask 的部署维持 retrieve-only。
- 意外收获：REST 的 `SearchParams`（[types/search.go:237](internal/types/search.go#L237)）**已支持 `knowledge_ids`（文档级过滤）和 `knowledge_base_ids`（同模型多库一次查）**——刚做完的 1.11 文档级搜索能力，走 REST 也能做到，不需要等 Go 侧任何改动。
- 唯一一个 REST 没直接给的能力：**read_document 的"文内关键词定位"和 grep_chunks 的正则**。REST 只有分片分页（`page/page_size/chunk_type`），没有 query 参数。侧车在 Python 侧翻页拉取、内存匹配即可（内置 Go MCP 的 grep 本质也是"索引取候选+内存正则"，不是库端正则）。

**结论：输入输出稳定性满足你的要求。** 风险边界清楚：我们依赖的是公开 REST + 两张表的固定列，不依赖任何 Go 内部 struct/接口。WeKnora 后续升版本，按上表做一次冒烟即可；真有变化，改动收敛在侧车每个工具的一个适配函数里。

### 2.4 现有二开资产盘点（哪些直接复用）

| 资产 | 侧车是否复用 |
|---|---|
| `mcp_endpoints` 表（令牌哈希、库白名单、工具白名单、默认 agent、限流） | **只读直连**。管理面 UI 继续用，侧车不另起炉灶 |
| `mcp_user_permission` 表（千机 upsert，一用户一行授权库数组） | **只读直连**，沿用 45s 短缓存 + 无负缓存策略 |

| Go 内置 mcpserver 的用户校验那套二开代码 | 不依赖、暂不删 |

## 三、目标架构

### 3.1 总图

```
┌──────────────────────┐   ┌──────────────────────┐
│ Claude Desktop 等    │   │ 千机网关 → OpenCode   │
│ 不区分用户的客户端     │   │ （单进程目录分区）     │
└──────────┬───────────┘   └──────────┬───────────┘
           │ Bearer mcp_xxx           │ Bearer mcp_xxx.<JWT>
           ▼                          ▼
        ┌─────────────────────────────────────────┐
        │   mcp-sidecar（Python，独立容器/进程）     │
        │  ASGI 鉴权中间件（拆凭证→端点→凭证自识别）  │
        │  MCPServer 2.3：9 个只读工具，无状态 HTTP   │
        │  工具白名单 ∩（公共书架∪用户授权）∩限流∩审计│
        └───────┬──────────────────┬──────────────┘
                │ REST X-API-Key    │ 只读 SELECT（固定列）
                ▼                  ▼
      /api/v1（WeKnora Go）    mcp_endpoints /
      检索/文档/wiki/问答/入库  mcp_user_permission
                │                  ▲
                ▼                  │ 只读，45s 缓存
           PostgreSQL ◄────────────┘
           Redis（滑窗限流，复用现有实例）
```

### 3.2 单次 tools/call 处理链

1. ASGI 中间件：取 Bearer；在第一个 `.` 切分（端点令牌字符集 base64url 无点，JWT 恒含两个点，无歧义）。
2. 左段 sha256 hex 常量时间比对 `mcp_endpoints.token_hash` → 端点行（enabled、deleted_at 为空）。**单 URL 的奥秘：端点身份由令牌反查，不需要路径里带 endpoint_id。**
3. **凭证自识别**（2026-11-03 修订，见 §4.2）：无右段 → 机器主体（user_id=None）；右段有 JWT → 验签 + type/tid/aud 交叉校验，通过则得到外部 user_id，**票存在但非法一律 401，不降级为机器主体**。
4. tools/list：按端点工具白名单过滤；可见库 = 端点公共书架（机器）或公共书架 ∪ 个人授权（用户，授权表读取失败时 tools/list 失败，fail-closed；个人授权为空仍展示公共书架）。
5. tools/call：工具白名单 → 生效范围（机器=公共书架；用户=公共书架∪个人授权，frozenset 并集自动去重，授权表失败 fail-closed）→ Redis 滑窗限流（额度取端点 rate_limit_per_minute，**Redis 不可用时进程内内存兜底**，与内置 Go 限流器一致；多副本时兜底仅按本副本计数，可用性优先于精确性）→ 审计日志（allow/deny，含 user_id/tool/kb）→ 执行。空范围（公共书架与个人授权都为空）guard 放行，由工具层以 "no knowledge base is available on this endpoint" 拒绝具体调用。
6. 工具执行：scope 为闭集，解析库选择器（id 或精确库名，在"生效范围 ∩ 实时 REST 可见库"内匹配；范围外选择器直接 ScopeError，**不触发范围外的详情 GET 探测**）；文档级操作先 GET /knowledge/:id 反查所属库做越权校验；然后调 REST、转换输出。
7. 多轮 ask 的 session_id 用**侧车自签名的不透明票据**下发（内含 weknora 真实 session id + endpoint + user，HMAC 签名），不带状态表，续问验签即完成归属校验。

### 3.3 为什么这是"最不怕升级"的形态

- 升级震动从大到小排序：**Go 内部 service 接口/agent 工具（每个版本都在动）> DB 表结构（缓慢加列）> 公开 REST（只做加法）**。侧车只站在后两档。
- 内置 Go MCP 现在直接吃 `SearchTargets/WikiScope/scopedKBContext/EventBus/URL 改写器` 这些内部结构，官方每次改检索管线，二开合并都要人工对冲突；侧车完全没有这类耦合。
- 侧车自身版本独立：pyproject 锁版本、契约自带测试（pytest + respx 模拟 REST），WeKnora 升级后跑一遍 9 工具契约测试即可放行。

## 四、凭证与身份设计（一个密钥）

### 4.1 凭证形态

| 客户端类型 | 配置内容 | 侧车识别结果 |
|---|---|---|
| 不区分用户（Claude Desktop、脚本） | URL + `mcp_xxx` 一个密钥 | 机器主体，可见库=端点公共书架（`knowledge_base_ids`；留空=零库） |
| 区分用户（千机/OpenCode 网关） | URL + `mcp_xxx.<JWT>` 一个密钥 | 用户主体（机器主体之上叠加 user_id），可见库=公共书架 ∪ 该用户个人授权 |

- **任意端点同时接受两种凭证**（2026-11-03 修订）：模式不按端点配置，现场看凭证里有没有合法票。
- 双因子强度不降级：用户模式仍需同时持有①端点静态密钥 ②JWT_SECRET 签发能力，两个秘密缺一不可。
- 全部走标准 Authorization 头，任何只有一个 API Key 输入框的 MCP 客户端都能配。
- user_id 只从验签后的 JWT 取，**绝不从工具参数/URL/请求体取**；每请求局部传递（Python 用 contextvars，不用全局变量）。

### 4.2 身份模式：凭证自识别 + 公共书架并集（2026-11-03 修订，已实施）

> **大白话：不再让管理员维护"哪个端点要票、哪个不要票"的名单了。同一把端点钥匙，请求里没票就是机器人（只看端点开放的公共书架），票验过了就是具体某个千机用户（公共书架 + 他个人被授权的库，两份书单合并去重）；票要是填了却过期/伪造/签给别的端点，直接 401，绝不放他以机器人身份混进去。**

不往数据库加列，也不再读任何配置文件（2026-11-02 的 identity.yaml 端点名单方案已废弃，代码与样例文件已删除；废弃理由见 §十三 7）。模式由请求凭证现场决定：

- 裸 `mcp_xxx`（无点段）= **机器模式**：`user_id=None`，生效范围 = 端点 `knowledge_base_ids`（公共书架）；
- `mcp_xxx.<JWT>` 且验签通过（HS256、type=mcp_user_identity、exp/iat/sub 齐全、tid=端点租户、aud=端点 id、30s 时钟容差）= **用户模式**：生效范围 = 公共书架 ∪ 该用户在 `mcp_user_permission` 中的个人授权；
- 复合段存在但验票失败（伪造/过期/type 错/tid 或 aud 不符）= **401**，不降级机器模式（堵"塞乱票蹭公共书架/探测端点"）；
- 个人授权为空的合法用户：放行，仍可见公共书架（并集语义）；公共书架也为空时 guard 仍放行、scope 为空集，具体工具调用由工具层以 "no knowledge base is available on this endpoint" 拒绝；
- 公共书架留空 = 机器主体**零库**（取消旧设计"留空=工作空间全部库"的语义；需要开箱可测的公共库时，运维建库并把 id 填进端点 `knowledge_base_ids` 即可，不硬编码任何默认库）；
- 用户授权表读取失败 = **fail-closed**（拒绝本次调用），不降级为仅公共书架；
- 错误文案统一 401 invalid credential，不区分是端点令牌还是票段出错（防分段探测）。

裁决矩阵（同一个端点、同一把钥匙）：

| 客户端发送 | 识别结果 | 生效范围 |
|---|---|---|
| 仅 `mcp_xxx` | ✅ 机器模式 | 公共书架（留空=零库） |
| `mcp_xxx.<合法JWT>`（个人授权含 kb-c） | ✅ 用户模式 | 公共书架 ∪ 个人授权（去重） |
| `mcp_xxx.<合法JWT>`（个人授权为空） | ✅ 用户模式 | = 公共书架（可能为空集） |
| `mcp_xxx.<JWT 非法/过期/type 错/tid/aud 不符>` | ❌ 401 | —— |
| 过渡期旧头 `X-User-Credential: <JWT>` + 裸 `mcp_xxx` | 同复合票规则（坏票同样 401） | 同上 |

**安全性论证**：机器范围恒为同端点任意用户范围的子集（公共书架 ⊆ 公共书架∪个人授权）。因此网关漏发/错发票据只会让可见库变少，永不越权；端点后台的 KBAccessRead 仍是最终裁判，公共书架里点名了但实际未共享给本工作空间的库，详情补查会被后端挡掉、静默不可见。

（2026-11-02 曾在三条路中选择 identity.yaml 名单；同日评估过的另两条——数据库加 identity_mode 列、按授权表有无行派生——2026-11-03 起实际采用的是"凭证自识别"这条第四条路，理由与拍板原话见 §十三 7-9。）

### 4.3 网关改造与灰度（2026-11-03 修订：无名单、无开关、无需重启）

> **大白话：上线侧车后机器人立刻能用；网关什么时候改完拼接票据，用户模式什么时候生效，两边各走各的、互不卡脖子，也不需要管理员在中间拨任何开关。**

- 网关最终形态只改一行：`Authorization: Bearer mcp_xxx + "." + 现有IssueMCPUserTicket(...)`，签票逻辑（5 分钟 TTL、逐请求签、tid 固定、aud=端点）原样不动。
- 灰度三步（同一个端点、同一把钥匙，全程不换配置、不重启）：
  1. 侧车上线、网关不动：裸 `mcp_xxx` 即机器模式，先把 9 个只读工具链路全部调通（公共书架可先挂一个公共测试库）；
  2. 网关发布"拼接复合票"改动：发合法复合票即用户模式，按公共书架 ∪ 个人授权返回；
  3. 网关切完后，删除旧 `X-User-Credential` 头兼容代码（纯减法，另排期）。
- 回退也只在网关一侧：不再拼票即回到机器模式；侧车与数据库无需任何动作。
- **过渡期侧车同时接受旧形态**：复合段缺失时回退读一次旧 `X-User-Credential` 头（走同一个验票函数，坏票同样 401），让"网关发布拼接票"与"旧头下线"解耦。
- 单进程目录分区方案里各用户目录的 opencode.jsonc：URL 全相同，只有 Bearer 不同；"凭证不进目录配置、由本地代理注入"的做法继续成立，只是注入的头从两个变一个。

### 4.4 fail-closed 与审计（与现二开语义对齐）

- 无端点/令牌错/端点禁用 → 401（不可区分）；工作空间停用 → 403；端点反查 DB 故障 → 503。
- 带票而验票失败（含旧头票）→ 401，绝不降级机器模式；**用户模式下授权服务（DB）不可用 → 拒绝，绝不降级为仅公共书架**；个人授权为空不再拒绝（仍可见公共书架，见 §4.2）；公共书架与个人授权皆空时，tools/list 给空集、tools/call 在工具层以"无可用知识库"拒绝。
- 每次 tools/call 一条 JSON 审计：`verdict/user_id/endpoint_id/tool/kb_id/doc_id/deny_reason`，输出到容器 stdout（走现有日志收集）。
- 授权查询沿用 45s 缓存、空结果不缓存（收权即时生效）、定期 sweep。

## 七、数据与迁移：零迁移

## 九、安全清单（实施验收项）

1. Bearer 不落 query、不入日志原文；JWT 验签强制 HS256 + aud/tid 绑定 + 过期 + type 隔离。
2. 机器可见域=端点公共书架本身，任何模式下都拿不到用户个人授权（机器范围恒为用户范围子集，坏票 401 不降级是该性质的边界守卫）。
3. 文档级工具先 GET /knowledge/:id 反查 `knowledge_base_id` ∈ 授权集，再执行；v1.1 下载工具同样先做归属校验。
4. 侧车是 X-API-Key 唯一持有者：该 key 默认仅授 retrieve，开放 ask 才加 chat（绝不授 full access，ask 请求体永不带 web_search_enabled）；DB 账号只读两表；容器非 root；/healthz 不泄露配置。
5. ask 永远不下发联网开关；agent 只取自端点配置；多轮票据验签防跨用户/跨端点串会话。
6. knowledge_ids≤100、各类 limit 钳制与现内置一致；请求体大小限制用 SDK 内置参数。
7. 红队用例（实施后必跑，已进单测矩阵）：无票/伪票/过期票/跨端点票/跨租户票/错 type 票/**塞坏票试探降级（必须 401，不能掉回机器模式）**/文档 id 越权/库名伪装/裸 token 偷看用户个人授权/空范围选择器探测（不得触发范围外详情 GET）。

## 十、与内置 Go MCP 的关系与切换计划

1. **阶段一并存**：Go `/mcp/:endpoint_id` 不动；侧车 `/mcp` 新起。灰度按 §4.3 三步（裸 key 机器模式调通 → 网关切复合票 → 旧头下线），全程无名单开关、不重启。
2. **阶段二切换**：OpenCode 目录配置/网关指向侧车；跑 9 工具契约 + 四条端到端（裸 key 机器调用、复合 key 用户调用、坏票 401 不降级、越权拒绝）。
3. **阶段三下旧**：确认无流量后，Go 内置 MCP 路由通过配置/注释下线（届时再单独评估，本期不动 Go 代码）。管理后台、mcp_endpoints 表继续保留使用。
4. 回滚成本极低：客户端配置指回原 URL 即恢复，侧车无任何写库动作。

## 十二、风险与限制（如实列明）

1. REST 检索结果的排序/富化不如内置直连精细（MMR、预算裁剪、图片富化）；以"够用的问答检索"为目标，精细度列为 v2。
2. read_document 长文档 query 模式需要多次 REST 翻页，有页数上限；超长文档定位可能 truncated（会显式告知）。
3. 侧车是新运行时（Python 进程），多一个要监控/升级的组件；但它无状态、可多副本（限流在 Redis），挂了不影响 WeKnora 本体。
4. WeKnora REST 返回信封（success/data/total…）若未来大改，适配层要跟——但四版本事实是只做加法，风险低，且有契约测试兜底。
5. 旧官方 Python 包（mcp-server/，31 工具）继续弃用状态，本方案不复活它，只借骨架。
6. 图片私有链接、原始文件下载的端到端可达性需联调实测：图片先透传、必要时 v2 做签名代理；原件下载 v1.1 以预签名链接形态提供（不塞二进制进 MCP 返回）。
7. 凭证自识别模型下没有名单同步成本，但**公共书架的语义与内置 Go MCP 刻意分叉**：Go 端仍是"端点库白名单 ∩ 用户授权"且空=全工作空间，侧车是"公共书架 ∪ 个人授权"且空=零库；两 MCP 并存期间文档/排障必须说清这一差异，Go 内置 MCP 下线后本条随之失效（见 §十三 10）。
8. 纯只读取舍：问答之外的入库需求仍走管理后台/现有 API，这是刻意收敛而非缺陷。

### 2026-11-03 修订（已实施，213 个单测全过）

> **大白话总览：管理员再也不用维护"哪些端点要票"的名单——任何端点都同时接待机器和用户，有没有票看请求本身；端点开放的库改成"公共书架"，机器只看书架上的，用户看书架加自己的，合并去重；书架空着就不给机器任何库。**

7. **废止 identity.yaml，改为单端点凭证自识别**：
   - 通俗说：不用再给每个端点贴"机器专用/用户专用"标签了；同一把钥匙，没票就是机器、有合法票就是用户，贴标签的配置文件、加载器、样例和 `IDENTITY_CONFIG_FILE` 环境变量全部删除（连带去掉 PyYAML 依赖）。
   - 原话依据："无论是机器还是千机这个场景的用户，都是使用的同一个 mcp……无论你使用哪种认证方式，我先识别，有 JWT 则走用户专属模式，无则走普通模式。"
   - 票存在但非法（伪造/过期/错 type/tid/aud 不符）一律 **401，禁止静默降级机器模式**。
8. **库范围从交集改为公共书架并集，空书架=零库**：
   - 通俗说：端点的 `knowledge_base_ids` 改名叫"公共书架"用——谁拿着钥匙都能看；用户个人授权的库再往上加，两份书单**取并集、frozenset 自动去重**；个人一本都没被授权的用户照样能看书架；书架一本都不放，机器就一本都看不到（不再是旧设计的"空=全工作空间"）。
   - 原话依据："端点开放一些任何机器人和用户都可以访问的知识库或者不开放任何知识库，以千机方用户具备的知识库权限来获取，所以取并集是最好的方式。"
   - fail-closed 保留：用户模式下授权表读取失败 = 拒绝，不降级为仅公共书架。
   - 公共测试库不硬编码：需要开箱可测时运维建库、把 id 填入端点 `knowledge_base_ids`。
9. **灰度简化为"网关单边改一行"**：无名单、无开关、无重启；裸票链路先行，网关发复合票即切换，不拼票即回退；旧 `X-User-Credential` 头过渡期保留（坏票同 401），网关切完后单独删代码。
10. **ask 库范围闭集钉死 + 与 Go 内置 MCP 刻意分叉**：ask 请求体的库列表一律来自 guard 生效闭集，智能体自带的 kb 配置不再生效（否则 ask 可绕过范围）；侧车并集/空=零库语义与待下线的 Go 内置 MCP（交集/空=全部）不同，差异写入本文件、README 与部署手册，Go 端代码一行不动。
